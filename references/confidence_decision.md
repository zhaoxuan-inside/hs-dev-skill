# 置信度决策协议（Confidence-Gated Decision）

本协议约束 Agent：**先评估置信度，再决定自主推进或向开发者询问**。目标是少打扰、不瞎猜——通用方案直接落地；仅在项目特有且选项难分高下时停下来让人决策。

与 7 阶段生命周期正交：任何阶段、任何设计/选型/实现分叉，在落盘或编码前都先过本协议。  
与 [技术学习 / 偏好记忆 / GitHub 对标](learn_and_prefer.md) 配套：用学习与偏好抬高置信、压低询问频率。

---

## 1. 决策前检查（强制顺序）

对每一个尚未由用户当场拍板的选择点，按序执行：

1. **检索既有资料**：会话、PRD、ADR、架构/接口/方法设计、词典、任务 detail、handoff、相关代码；**以及全局** `Path.home()/.hs-dev-skill/preferences.yaml`、`tech_learning/`（Win/Linux/macOS，见 `cross_platform.md`）与项目 `_01_dev_rule/`。
2. **偏好命中则停问**：全局偏好账本中同一类事情已有记录 → 按偏好执行（条件 C 视为不成立），禁止再问。
3. **新技术 / 模糊 UI·技术描述**：先按 `learn_and_prefer.md` 完成技术学习（写入全局 `tech_learning/`）与/或 GitHub 高星对标，再继续；禁止跳过对标直接臆造。
4. **判定是否通用解**：行业/语言/框架常见默认、本 Skill 强制规范、已有 ADR/选型可继承项、高星项目已成为事实标准的做法。
5. **自评置信度**：对每个可行选项给出 0–100 的相对置信，并标出首选与次选差距（学习/对标/偏好命中应显著抬高对应选项）。
6. **套用询问闸门**（见 §2）：不满足则**禁止提问、自主决策并落盘**；满足则**禁止猜测、结构化询问**。

---

## 2. 询问闸门（必须同时满足才询问）

**仅当以下四条全部为真时，才向开发者提问；否则自主决策并继续推进：**

| # | 条件 | 说明 |
|---|---|---|
| A | **影响面广** | 会显著改变对外契约、数据模型持久化形态、跨模块边界、核心业务语义、不可逆迁移或长期运维成本 |
| B | **项目特有** | 取决于本产品业务规则、组织约束或领域习惯，而非「大家通用」的工程惯例 |
| C | **资料未提及** | 用户此前所有资料（本会话 + 全局 `~/.hs-dev-skill/preferences.yaml` + 项目 `hs_dev_docs` + 相关代码）均未给出倾向或约束 |
| D | **置信接近** | 存在 ≥2 个可行选项，且最高置信与次高置信差距 **≤15**（难分高下）；学习/对标后差距拉大则不得再问 |

反例（**不要问，直接做**）：

- 通用解：REST 资源用复数路径、表含 `id/created_at/updated_at`、JSON 与项目既有风格一致、超时重试用指数退避等。
- 资料/偏好已写：PRD/ADR/词典或全局 `~/.hs-dev-skill/preferences.yaml` 已定支付渠道、已选 PostgreSQL、已定「UI 紧凑少卡片」。
- 高星对标收敛：GitHub 成熟方案高度一致且与栈契合 → 采纳并对齐文档。
- 置信明显倾斜：选项 A 置信 85、B 置信 55 → 选 A，在 ADR/设计中简述理由即可。
- 影响面窄：局部私有命名、单测夹具结构、注释措辞、与对外行为无关的内部拆分。

---

## 3. 置信度标定（供自评）

| 区间 | 含义 | 默认动作 |
|---|---|---|
| ≥80 | 高度确信（通用惯例、偏好命中、资料强支撑或高星对标收敛） | 自主决策，不询问 |
| 65–79 | 较有把握 | 自主决策；在设计/ADR 中用一两句记下假设 |
| 50–64 | 两可 | 若同时满足 §2 的 A+B+C 且与次选差距 ≤15 → 询问；否则取最高置信并注明假设 |
| <50 | 依据不足 | 先补学习/GitHub 对标再重估；仍不足且满足 A+B+C → **必须询问**；影响面窄 → 选可逆保守默认并注明假设 |

「大家通用的解决方案」：即使未在项目资料中写明，只要符合主流工程惯例且与既有栈无冲突，视为置信 ≥80，**不询问**。

---

## 4. 询问时的行为（满足闸门时）

1. **停在决策点**：不落盘最终结论、不写死不可逆实现；任务已创建则 `status --set BLOCKED`（原因写清决策点）。
2. **一次只抛真正卡点**：合并相关问题，避免把通用项或已对标项塞进问卷。
3. **结构化提问**（每项）：
   - 决策点一句话；
   - 2–3 个选项 + 各自利弊与自评置信；
   - 标注影响面（契约 / 数据 / 边界 / 成本）；
   - 说明「资料/偏好中未找到依据」；若已做 GitHub 对标，附 1–2 个仓库与差异摘要。
4. **收到答复后**：
   - 写入 PRD/ADR/设计/词典中的对应位置；
   - **同步更新全局** `Path.home()/.hs-dev-skill/preferences.yaml`（跨项目、三端同一路径语义）；
   - 解除 `BLOCKED`，再继续阶段流转。

禁止：用「常见做法」静默填满项目特有业务规则；禁止在未满足闸门时打断用户确认显然项；禁止用户已表态后不写入全局偏好导致跨项目重复询问。

---

## 5. 与各阶段的衔接

| 阶段 | 典型自主项 | 典型需问项（仍须过 §2 四条件） |
|---|---|---|
| 0 需求 | 已由用户说清的流程整理成 PRD；通用异常；模糊 UI 经高星对标后的可执行规格 | 业务归属、计费/权限等特有规则、DoD 中资料未给的验收口径 |
| 1 选型 | 与已有栈一致的默认库；偏好命中；学完新技术后的主流集成；高星收敛方案 | 多栈均可且影响面广、资料与偏好无倾向、对标后仍置信接近 |
| 2 架构 | 标准分层、常规聚合拆分 | 限界上下文切割影响多团队/多端且选项接近 |
| 3 详设 | 强制字段、V/U 配对、常规索引与六元组骨架 | 对外 API 语义、持久化业务字段、补偿/资金类不可逆策略 |
| 4–6 | 任务拆解、TDD、门禁脚本 | 实现中新暴露的、仍满足 §2 的业务分叉 |

**阶段门禁**：产出物与索引齐套即可跃迁；**不再**要求每个阶段都做一次「全文请确认」。仅当本阶段存在仍打开的 §2 询问项时，必须等用户决策后再进入下一阶段。

阶段 0 特例：若用户只给了一句话需求，且核心场景/DoD 在资料中不存在，则场景与 DoD 通常同时满足 A–D，**应询问**；UI/技术形态模糊则先 GitHub 对标再决定是否还需问。已足够清晰时可直接产出 PRD 摘要并推进，摘要中列出「自主假设（通用/高置信）」供事后纠偏，而非阻塞等待。
