# 工程验收清单（选型到交付的文档标准）

**何时读**：阶段 1～6 开始/验收或工程变更；只装载当前阶段节。按 [阶段验收协议](stage_acceptance.md) 执行。
**来源**：[规范依据](standards_basis.md)；条目为项目化检查规则，不是任何外部标准的逐条符合性声明。

## 1. 通用输入与否决条件

每阶段记录输入文档版本、当前范围、检查项及验收证据。变更影响到已签收内容时先标失效并更新基线。产出须可追溯到需求；没有需求来源的工程扩展说明必要性，不能借规范擅自扩大范围。
以下均阻断：输入基线失效、关键问题未决、无证据、约定与实现矛盾、未授权改变业务目标。阶段提交给开发者验收，既有明确确认按范围复用。

## 2. 阶段 1：技术选型

输入：产品冻结基线及风险探查；产出：选型说明、ADR、验证证据、选型拍板记录。

| ID | 工作 todolist | 验收标准与所需证据 |
|---|---|---|
| TECH-01 | 建立约束对照 | 每项必须满足的能力、平台、数据、预算和质量约束映射到候选能力及证据，明确不满足项；沿用方案引用既有 ADR |
| TECH-02 | 比较实际可行方案 | 有取舍时比较候选的关键收益、代价、团队适配、迁移及退出成本；评分有依据，不用高星或凭空性能数字代替验证 |
| TECH-03 | 验证高风险能力 | 对 SDK/API、权限、环境兼容等影响结论的未知项有最小实验、版本、结果和限制；无法满足则回产品裁决 |
| TECH-04 | 锁定实施约束 | 指定 runtime/依赖版本范围、兼容性、部署前提、适用许可/费用限制；顶部契约与最终 ADR 一致，落选方案不混入执行契约 |
| TECH-05 | 验收选型决策 | 推荐理由追溯产品约束，风险有处理人/时点；开发者确认选型及不可逆取舍的具体版本 |

## 3. 阶段 2：架构设计

输入：需求、质量约束与选型基线；产出：架构说明、必要视图、ADR 关联、风险表。参照 arc42 的内容维度，按规模裁剪。

| ID | 工作 todolist | 验收标准与所需证据 |
|---|---|---|
| ARCH-01 | 定义上下文与边界 | 使用者、外部系统、输入输出、信任边界及本系统不承担的职责明确；与产品范围一致 |
| ARCH-02 | 分配职责与数据所有权 | 每个核心能力有负责模块，数据写入权、模块接口和依赖方向明确；避免职责重叠或无主业务规则 |
| ARCH-03 | 还原关键运行场景 | 核心成功/失败场景能映射至模块协作，适用的事务边界、异步顺序、重试与恢复有归属；不以静态目录树替代运行设计 |
| ARCH-04 | 描述部署与配置 | 目标运行环境、进程/服务依赖、配置/机密来源及启动顺序可解释；单机方案可用一张图，无需强造分布式系统 |
| ARCH-05 | 对应质量与安全约束 | 关键质量场景对应设计措施及验证计划；认证/授权位置与隔离边界明确；不因引用安全规范默认启用全部治理模式 |
| ARCH-06 | 验收权衡与风险 | ADR、已知风险/技术债、演进限制有记录；开发者确认系统边界和重要取舍，机器契约与视图一致 |

## 4. 阶段 3：详细设计

输入：产品/架构基线；产出：仅触达的 DB/API/方法/调用链契约及测试规格。OpenAPI 负责接口表达，不能替代业务规则。

| ID | 工作 todolist | 验收标准与所需证据 |
|---|---|---|
| DETAIL-01 | 设计数据约束 | 触达数据时明确字段含义、类型、空值/默认值、唯一性、关系、生命周期和访问模式；索引对应实际查询；迁移兼容、回退限制及开发者 DB 决策有记录 |
| DETAIL-02 | 定义接口契约 | 触达 API 时明确操作、认证、入参/响应 Schema、必填与空值、错误、示例；适用的分页/幂等/版本兼容明确；固定 Schema 方言，工具验证通过 |
| DETAIL-03 | 定义方法行为 | 前置条件、输入输出、后置条件、不变量、边界及副作用明确；按现有方法分类选用设计粒度，不凭规范新造通用方法 |
| DETAIL-04 | 定义状态与失败语义 | 适用的并发更新、重复请求、超时、部分失败、补偿、资源释放有精确结果与归属；重试有条件/上限，禁止默认无限重试 |
| DETAIL-05 | 建立跨文档映射 | REQ/规则 ↔ 接口 ↔ 数据 ↔ 方法/调用链 ↔ 验收场景一致；单位、精度、时间、枚举和权限语义无冲突 |
| DETAIL-06 | 验收实现准备度 | 关键业务决定无需编码者猜测；测试规格可区分正确/错误实现；开发者确认对外行为、数据设计和关键契约，其他项提交证据验收 |

## 5. 阶段 4：任务与上下文

输入：已验收设计；产出：任务、依赖、Context Pack 和需求映射。任务编排/版本失效规则为本 Skill 自定。

| ID | 工作 todolist | 验收标准与所需证据 |
|---|---|---|
| TASK-01 | 分配范围内全部需求 | 每个必需 REQ/场景映射任务与验收责任；无漏项、重复归属和未经确认的新功能 |
| TASK-02 | 定义可验证切片 | 每项有目标、边界、输入、输出、DoD、测试 seam；优先形成能验证业务结果的垂直切片，不只按前后端层分工 |
| TASK-03 | 排定依赖与风险 | 前置任务、外部条件、并行冲突、风险验证时点明确，无循环依赖；先处理可能推翻后续工作的未知项 |
| TASK-04 | 绑定有效上下文 | Pack 记录来源路径、版本/内容摘要、规则 ID、适用约束；切片覆盖所需规则且没有落选方案，源变更后必须重新对账 |
| TASK-05 | 验收执行计划 | 阶段验收点、演练点与需求覆盖表齐备；开发者确认切片顺序及交付边界，既有确认无需重复 |

## 6. 阶段 5：实现切片

输入：有效任务/Pack；产出：代码、同步文档、测试与演练记录。语言规则沿用 [coding_standards](coding_standards.md)；Java 检查补充见 §8。

| ID | 工作 todolist | 验收标准与所需证据 |
|---|---|---|
| IMPL-01 | 按行为红绿实现 | 逻辑变更有能暴露错误行为的测试及执行记录；接口/领域不变量得到验证，不能只断言内部调用次数 |
| IMPL-02 | 同步契约与变更 | 实现与 REQ、接口、Schema、状态规则一致；偏离已有裁决，未决产品空白回 DESIGN；迁移和派生 Pack 同步 |
| IMPL-03 | 检查语言与运行风险 | 适用静态检查通过，并人工核对异常、资源、并发、数据和安全风险；自动规则未覆盖的部分仍需证据 |
| IMPL-04 | 验证真实协作边界 | 适用的数据库/外部 Adapter/界面集成有结果；声明 Mock 范围，不以全 Mock 测试证明真实集成 |
| IMPL-05 | 演练高风险业务切片 | 用已确认样例核对真实运行结果；流程/权限/数据行为等重要偏差关闭后再复制到后续同类功能；无行为变化项可说明 NA |
| IMPL-06 | 提交切片验收 | 对应 DoD、差异与证据可逐项追溯，开发者确认业务预期；可将多个已展示切片合并验收，不能由 Agent 自称完成代签 |

## 7. 阶段 6：验证与交付

输入：实现基线与全部必需需求；产出：需求验证矩阵、测试报告、偏差表、交付说明。保留 [quality_gates](quality_gates.md) 的适用测试要求。

| ID | 工作 todolist | 验收标准与所需证据 |
|---|---|---|
| DELIV-01 | 回收完整需求基线 | 必需 REQ 全部映射实际断言与结果；分母与冻结基线一致；未实现/延期有开发者裁决，不能删行或写 verified 代替验证 |
| DELIV-02 | 记录测试执行 | 命令、环境、代码基线、执行时间、退出码、报告及失败/跳过原因完整；测试/静态检查按既有门禁通过，未执行不得标 PASS |
| DELIV-03 | 核对产品与质量场景 | 已确认的核心业务、异常恢复及适用质量/安全场景有结果；真实演练与自动测试相互补足 |
| DELIV-04 | 核对交付可用性 | 适用的安装、配置、启动、数据迁移和恢复说明可操作；产物与证据对应同一版本，限制与未实现项明确 |
| DELIV-05 | 验收交付结论 | 上游验收有效、阻断项清零；开发者确认本版本满足约定预期，才能记录交付 ACCEPTED 并完成任务归档 |

## 8. Java 编码补充检查

这是从阿里 P3C 公开条目提取风险后形成的项目检查，不是完整手册。旧 GitBook 与黄山版不一致；新项目锁定采用版本，现代 JDK/框架有差异时明确裁决，不能机械复制旧 API 建议。

| ID | 适用条件 | 检查与证据 |
|---|---|---|
| JAVA-01 | 有空值/类型边界 | 检查自动拆箱、集合元素、远程返回等空值路径及明确的边界测试；不靠捕获 NPE 代替契约 |
| JAVA-02 | 有异常/资源 | 按异常类型处理或传播、保留原因、正确关闭资源；捕获异常后的事务结果可验证，禁止吞错或 finally 返回掩盖结果 |
| JAVA-03 | 有共享状态/异步 | 明确线程安全、任务失败处理、线程池容量与拒绝策略；验证过载/异常，不使用无边界资源策略 |
| JAVA-04 | 有持久化唯一性/并发写 | 唯一性有数据库约束，更新冲突有明确策略；提供并发/重复写证据，不能只依赖“先查再插” |
| JAVA-05 | Java 项目 | 记录 P3C/PMD 或项目等价检查的版本、启用规则、运行结果和人工补检范围；插件通过不等于全部手册通过 |

Java 专属项在其他语言项目可 NA；通用风险继续按相应语言规范处理。
