# 开场确认协议（Opening Alignment）— 动手前与开发者对齐理解

**何时读**：受理任何**新需求/新任务**的会话第一步（先于分级、先于审讯、先于装载门闩 L1）；`intent=BUILD|REVERSE|FIX|REFACTOR` 均适用。  
**分工**：本文 = **需求理解 + 假设 + 约束 + 分级建议** 的先对齐；分级规则 → [`right_sizing.md`](right_sizing.md)；审讯编排 → [`grill_orchestration.md`](grill_orchestration.md)；装载门闩 → [`load_latch.md`](load_latch.md)。

---

## 0. 为什么必须有开场确认？

会话第一步如果直接进入「分级 → 门闩 → 审讯」，Agent 对用户一句话需求的理解**从未先请开发者确认**。一旦理解错位，后面的审讯问题都是「错的问题」，答得越多偏得越远，最后整链返工。  
**开场确认是本 Skill 返工率最低的一笔投入**：用 ≤10 行文字把理解钉死，把不可逆风险提前暴露。

**豁免**：`intent=EXPLORE`（只读）与 `intent=RESUME`（语义「继续」，沿用 plan_log）跳过本协议。

---

## 1. 步骤（O1～O4，≤10 行，一次完成）

```text
O1  需求复述：3～5 行复述「做什么 / 为谁 / 边界 / 关键动词」，并列出反目标（本期明确不做什么）
O2  假设与空白清单：列出当前不确定的产品语义、信息缺口、需要开发者输入的关键决策点（只登记，不求解）
O3  约束与干系人盘点：预算上限 / 排期硬点 / 合规要求 / 团队技术栈 / 可复用资产与数据 / 最终拍板人
O4  分级建议：给出 intent + change_size 建议与一句话理由（命中 DB 变更/不可逆/对外契约 → 至少 M/L），请开发者确认或修正
```

**每轮格式（强制）**：

```text
📋 **O1 需求复述**：…
🚫 反目标：…
❓ **O2 待澄清/信息缺口**：…（不求解，仅登记）
🔒 **O3 约束与干系人**：…
📐 **O4 分级建议**：intent=BUILD, change_size=M, work_mode=DESIGN（理由：新增业务触达数据库设计，须开发者决策）
➡️ 请确认或修正后继续。
```

**O4 必升档信号（命中即至少 M，触 DB 新增/破坏性迁移 → L）**：

- 新增业务/新功能**需要改动数据库设计**（新增表 / 改表结构 / 破坏性迁移 / 不可逆字段）——必须经开发者决策；
- 影响对外契约、持久化形状、权限/计费/归属等业务特有规则；
- 需求模糊、信息缺口大、或存在互相矛盾的需求表述。

---

## 2. 确认后

1. 结论写入任务 brief / context_pack 首行 / PRD 元数据（`intent` + `change_size` + `work_mode` + 已确认假设）。  
2. 进入 [`load_latch.md`](load_latch.md) L1/L2；`work_mode=DESIGN` 则继续 [`grill_orchestration.md`](grill_orchestration.md) 审讯。  
3. 开发者若推翻复述 → 立即修正，禁止带着错误理解继续。

---

## 3. 反模式

| 禁止 | 改为 |
|------|------|
| 需求一句话就直接进审讯/编码 | 先 O1 复述 + O4 分级建议，开发者确认 |
| 用「行业常识」脑补需求边界后开工 | 边界不明列进 O2 空白清单，向开发者求解 |
| 预算/排期/合规/团队栈全不盘点就选型 | O3 一次问清，作为阶段 1 选型输入 |
| 新增业务要改 DB 却自己定表结构 | O4 升档 + 走开发者决策（见 confidence_decision §1.5） |
| 对模糊需求判 S 想快点做完 | 需求模糊或信息缺口大 → 至少 M + DESIGN |

---

## 4. 与门闩 / 审讯 / 分级的衔接（一句话）

**O1～O4 是 L0 的前置**：先对齐「做什么」与「分级建议」，再写 `change_size`/`work_mode`、跑门闩索引、进审讯——确保所有后续问题都建立在已确认的理解之上。
