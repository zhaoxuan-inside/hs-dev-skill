# 阶段验收协议（文档标准与证据）

**何时读**：建立阶段计划、提交阶段验收、决定流转、续做或上游变更时。先读本协议，再只读当前阶段清单。
**目的**：Agent 驱动文档，已验收的文档驱动代码，证据与开发者确认决定阶段是否通过。

## 1. 执行入口

主 Skill 选择过程与功能后，由当前过程准备检查表，功能提供专业证据，acceptance 子 Skill 组织验收；三者都不能代签开发者确认。

| 阶段 | 验收清单 | 最小交付物 |
|---|---|---|
| 0A 需求理解与范围 | [需求与产品清单 §2](product_acceptance.md#2-0a-需求理解与范围) | 真实场景、预期对账、范围、假设与未决项 |
| 0B 产品设计与冻结 | [需求与产品清单 §3](product_acceptance.md#3-0b-产品设计与冻结) | PRD、规则/场景、适用的原型、冻结确认单 |
| 1 技术选型 | [工程清单 §2](engineering_acceptance.md#2-阶段-1技术选型) | 约束对照、ADR、风险验证结果 |
| 2 架构设计 | [工程清单 §3](engineering_acceptance.md#3-阶段-2架构设计) | 边界、职责、运行/部署视图、决策与风险 |
| 3 详细设计 | [工程清单 §4](engineering_acceptance.md#4-阶段-3详细设计) | 适用的数据、接口、方法、状态与异常契约 |
| 4 任务拆解 | [工程清单 §5](engineering_acceptance.md#5-阶段-4任务与上下文) | 需求到任务映射、依赖、DoD、Context Pack |
| 5 实现切片 | [工程清单 §6](engineering_acceptance.md#6-阶段-5实现切片) | 代码、同步契约、测试与切片演练证据 |
| 6 验证交付 | [工程清单 §7](engineering_acceptance.md#7-阶段-6验证与交付) | 需求验证矩阵、执行报告、偏差与交付说明 |

0A/0B 是阶段 0 内的两个验收点，不重命名生命周期原有的 0A/0A'/0B/0C 工作步骤。
上述清单是本 Skill 的项目规则；来源及阅读范围见 [规范依据](standards_basis.md)。

## 2. 工作完成与验收通过分开

1. 开始阶段时复制当前清单到 [阶段验收记录模板](../resources/templates/process/stage_acceptance.md)，将每条规则展开为工作 todolist；保留规则 ID。
2. 确定输入文档及版本、适用项、通过标准、证据形式和验收责任；不可等产出写完后降低标准。
3. Agent 完成工作后逐条提供证据、反例检查和候选结果，只能提交 `SUBMITTED`。
4. 工具执行可机械检查的项；开发者核对业务预期、关键取舍和阶段结论。按清单提交摘要与证据，不要求重读整份正文。
5. 有可追溯的开发者验收记录后，才可记为 `ACCEPTED` 并进入依赖该基线的下一阶段。一次答复可验收多个明确列出的阶段及版本；既有明确确认直接复用，禁止重复索取。

**所有实际执行的阶段都有验收记录。** S 可在既有任务/交付说明中内联，M/L 可放在当前阶段文档末尾，不新造一套目录。S/M 仍按 [right_sizing](right_sizing.md) 跳过无关阶段，跳过项写原因及沿用基线。EXPLORE 豁免；FIX/REFACTOR/REVERSE 沿各自路径，为实际交付物选用对应检查项，不强制补产品全套；RESUME 核对既有验收是否失效。

### 2.1 阶段完成时的完整文档清单

每个实际阶段（含 0A/0B、实现切片和 FIX/REFACTOR/REVERSE 的实际验收点）工作完成并提交验收时，**必须在面向开发者的回复中**展示该阶段全部待验收文档。不能只写报告路径、目录、通配符、若干示例或“详见附件”。多阶段一起提交时按阶段分别列出；S 可在同一记录内分节，不新增空文档。EXPLORE 不要求阶段验收。

1. 从本阶段计划/DoD、适用 checklist、实际产出和证据引用合并清单，包含阶段验收记录本身、待确认的设计/契约/原型/任务 Pack、需审阅的测试报告与交付说明。沿用输入单独标明“已验收基线”，不要混为本次待签收项；共享文档在各适用阶段列出并标注共用。
2. 每项展示 **文件名 + 可见的完整绝对路径 + 版本/内容摘要 + 审阅范围/规则 ID + 状态**。文件名用链接时，仍须在表格中明文列出全路径；内联记录注明所在文档及标题锚点。路径以真实工程根/安装根解析，不硬编码开发机路径。
3. 提交前检查路径存在且为可读文件、去重，并核对清单与本阶段计划/产出是否一致。应交未交的文档逐项列为 `MISSING` 并标出阻断，不隐藏也不伪造文件。代码和二进制资产按证据引用列出，不要求转成文档。
4. 默认状态为 `SUBMITTED`，区分“工作已完成，待验收”与“已验收”。同时说明候选结果、阻断项、沿用确认与下一动作；清单展示不构成开发者签收。已确认阶段仍展示文档及真实状态，不重复索取相同确认。
5. 文档发生变化或换工程根后重新生成路径/摘要；记录中保留相对路径便于迁移。回复里的绝对路径供定位，摘要绑定提交版本。自引用验收记录的摘要以最终保存后的工具输出为准，不把其自身摘要回写进同一文件。

回复表格：

| 阶段 | 文档名 | 完整绝对路径 | 版本/内容摘要 | 审阅范围 | 状态 |
|---|---|---|---|---|---|
| {阶段} | {文件名及链接} | {真实绝对路径} | {版本/sha256} | {规则ID/标题} | SUBMITTED / ACCEPTED / MISSING |

可用只读工具校验明确列出的文件并生成名称、路径和 SHA-256 表格：

```bash
python <安装根>/scripts/stage_review.py --root <工程根> --stage 3 --document hs_dev_docs/design.md --document hs_dev_docs/acceptance.md
```

工具不扫描全目录，不推断本阶段应该有哪些文档，也不验证业务正确性或验收状态；**清单完整性仍由过程负责人按第 1 项核对**。缺文件返回非零退出码，必须补齐或如实提交阻断。

## 3. 判定与权限

| 对象 | 状态 | 规则 |
|---|---|---|
| 检查项 | `PENDING / PASS / FAIL / NA` | 默认 PENDING；PASS 必须有证据与核对方式；NA 必须有适用性理由及验收人认可 |
| 阶段验收 | `DRAFT / SUBMITTED / REJECTED / ACCEPTED / INVALIDATED` | 默认 DRAFT；验收结论与任务工作状态分开，不增改 task_manager 状态枚举 |

- Agent 可以编写、分析、提出候选 PASS，不能将自检或另一个模型的赞同伪造成开发者签收。
- 工具能证明结构、链接、Schema、测试执行结果；不能证明业务符合开发者预期。
- 开发者确认必须绑定阶段、文档版本、范围和相关检查项；不要求手写签字，明确的会话答复可记消息位置/时间及原文。
- “继续”只有在紧邻消息清楚列出待验收阶段、版本和结论时，才可解释为该范围的确认；沉默和未反对均不算确认。
- 如开发者预先明确委托某阶段的技术验收，记录受托人/规则、范围及证据要求；不得据此代签业务、范围、DB 和关键契约决策。无此委托时提交开发者验收。
- 通过条件：适用检查项全部 PASS，NA 均有理由，无未关闭的阻断问题，且验收权限满足。禁止平均打分、完成百分比或模板齐套抵消关键失败。

## 4. 证据规则

- 文档证据：相对路径 + 版本/内容摘要 + 标题锚点 + 关联 REQ/场景/决策 ID；“见 PRD”“已检查”不合格。
- 运行证据：命令、环境、时间、退出码、结果位置、代码 commit 或工作树内容摘要。尚未提交可使用内容摘要，提交后补 commit。
- 预期证据：开发者陈述与确认记录；真实用户研究若未开展，明确写“开发者代理确认”，不能虚构访谈。
- 可逆低风险未知项可登记负责人、处理时点及不影响当前结论的理由；影响范围、业务流程、对外契约、数据安全或结构的未知项必须先关闭。
- 需求覆盖的分母来自已验收需求基线；缺失映射即失败。不能删除未实现项，或仅把状态改为 verified。

## 5. 变更与失效

机器登记、完整需求分母、源摘要与传递失效、旧记录迁移见 [workflow_improvement §2](workflow_improvement.md#2-需求基线与派生物)。验收记录须绑定当前需求基线、任务全部需求证据及已登记派生产物；测试证据绑定报告摘要。未登记或失效不能完成归档。

源文档变更 → 对比语义差异 → 列出受影响的规则/场景/决策 → 将关联验收和派生 Context Pack 标为 INVALIDATED → 更新文档与证据 → 对受影响项重新验收。纯排版变化记录“不影响语义”的依据，可保留原签收。

发现原理解不符合先前表达时，记录为“理解偏差/遗漏”；开发者改变已确认目标时记为“需求变化”。二者都走 [变更通道](requirement_change.md)，但不能把前期遗漏归咎于用户新增需求。

## 6. 与现有门禁的关系

本协议取代“产出齐套 + 无询问项即可自动流转”的旧阶段判定；各领域技术规范和测试门禁仍适用。阶段 0 的冻结确认单是该阶段的人类签收凭据，其他阶段使用通用记录。

`task_manager.py` 在任务归档为 `COMPLETED` 前会校验结构化验收记录、DoD、REQ 状态并运行严格一致性门禁；它不能鉴别确认是否真实来自开发者，也不会运行项目专属测试。测试命令和结果必须记录在验收记录，Agent 不得伪造。脚本退出成功不等于阶段验收成功；禁止声称机器已经验证人的真实意图或外部标准合规认证。
