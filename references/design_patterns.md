## 1. 核心理念：深模块哲学与“反模式狂热”

经典设计模式（GoF 23 种模式）是解决特定软件复杂度的利器。然而在 AI 辅助与 VibeCoding 场景下，极易滑向两大极端：
1. **面条代码（No Design）**：AI 遇事不决直接堆砌嵌套 `if-else` 或写几百行巨型函数，破坏内聚性；
2. **模式狂热（Over-engineering）**：为了一个只有 2 行分支的简单逻辑，凭空创造抽象类、工厂与多个子类，制造大量空心“浅模块”。

### 深模块反过度设计铁律
- **“一个 Adapter 是假想缝，两个 Adapter 才是真缝”**：若系统中没有第二个实现（也没有 Fake 测验诉求），禁止为“架构美感”凭空建抽象接口；
- **小接口 + 厚实现**：设计模式内部复杂的拓扑关系必须收敛在模块内部，对外暴露的调用入口必须极致简单；
- **S 级变更克制**：`change_size=S`（< 50 行修复）严禁重构引入重型模式；仅 M/L 级涉及复杂业务分流或外部多端接入时，才在阶段 2/3 显式引入模式。

## 2. 代码异味（Code Smell）→ 设计模式选型决策树

在阶段 3 详细设计或重构时，依据代码异味定位最适合的设计模式：

```text
[识别代码异味或业务痛点]
  │
  ├─ 多个同构业务分支/复杂计价规则/动态算法 ──────────────▶ 【策略模式 Strategy】 (ALGO 原型)
  ├─ 前置鉴权/风控拦截/参数多级校验流水线 ───────────────▶ 【责任链模式 Chain of Resp.】 (GUARD 原型)
  ├─ 实体状态交织跃迁/非法跳转防范 ─────────────────────▶ 【状态模式 State】 (STATE 原型)
  ├─ 方法参数超过 4 个/可选配置繁杂 ───────────────────▶ 【建造者模式 Builder】 (TRANSFORM 原型)
  ├─ 依赖易变第三方 SDK/外部系统防腐 ─────────────────▶ 【适配器模式 Adapter】 (ADAPTER 原型)
  ├─ 子系统接口琐碎/外部调用成本高 ────────────────────▶ 【外观门面模式 Facade】 (ORCHESTRATE 原型)
  ├─ 主干流程完成后需触发多重从属异步动作 ───────────────▶ 【发布-订阅模式 Pub/Sub】 (调用链解耦)
  ├─ 业务骨架固定但局部差异算法需定制 ──────────────────▶ 【模板方法 Template Method】 (ORCHESTRATE/ALGO)
  ├─ 监控/缓存/限流/重试等横切逻辑污染核心 ──────────────▶ 【装饰器/代理模式 Decorator/Proxy】
  ├─ 树状层级遍历/组织架构/嵌套规则 ───────────────────▶ 【组合模式 Composite】
  └─ 跨服务/长流程一致性与逆序回滚 ───────────────────▶ 【Saga 编排模式】 (六元组运行时)
```

## 3. GoF 经典设计模式速查与方法原型映射

### 3.1 创建型模式 (Creational) —— 规范对象构建
| 模式 | 解决的核心问题 | 落地形态与规范 | 对应原型 |
|---|---|---|---|
| **Builder (建造者)** | 构造器参数膨胀（>4 个），避免传参错位 | 提供流式 `setXxx()`，在最终 `build()` 中执行不变量校验 | `TRANSFORM` |
| **Factory Method (工厂)** | 解耦调用方与具体类的直接 `new` 依赖 | 依据类型或租户标识路由具体实现实例 | `ALGO` / `TRANSFORM` |
| **Singleton (单例)** | 连接池、配置中心等全局昂贵资源复用 | 保证单例唯一性，但**必须通过依赖注入注入接缝，严禁滥用全局静态变量**破坏单测 | `ADAPTER` |

### 3.2 结构型模式 (Structural) —— 规范模块装配
| 模式 | 解决的核心问题 | 落地形态与规范 | 对应原型 |
|---|---|---|---|
| **Adapter (适配器)** | 第三方/外部接口异构、易变、不符合规范 | **强制防腐层 (ACL)**：隔离外部毒素，对外提供纯洁业务接口 | `ADAPTER` |
| **Facade (门面)** | 子系统接口细碎，调用方难以使用 | 聚合调度多个子方法，对外提供“一键式”高杠杆接口 | `ORCHESTRATE` |
| **Decorator / Proxy** | 横切逻辑（日志/缓存/限流/监控）侵入业务代码 | 保持核心业务方法纯粹，在外围包裹增强处理 | `ADAPTER` / `GUARD` |
| **Composite (组合)** | 统一处理单个叶子节点与复合树状节点 | 统一操作接口，消除客户端繁复的递归判断逻辑 | `TRANSFORM` |

### 3.3 行为型模式 (Behavioral) —— 规范控制流与算法
| 模式 | 解决的核心问题 | 落地形态与规范 | 对应原型 |
|---|---|---|---|
| **Strategy (策略)** | 消除复杂 `if-else / switch` 算法分支 | 策略接口定义纯函数契约，具体策略独立封装，通过工厂/注册表获取 | `ALGO` |
| **Chain of Resp. (责任链)** | 多层顺序校验与短路拦截 | 拆解为单一责任的 Handler，支持按需组装链条与提前中断 | `GUARD` |
| **State (状态)** | 实体复杂生命周期流转与合法跃迁控制 | 状态对象驱动行为，事件触发内存跃迁，杜绝非法状态跳变 | `STATE` |
| **Pub/Sub (发布订阅)** | 主流程解耦从属异步通知，避免大事务 | 领域事件（Domain Event）驱动，配合 Outbox 模式保证一致性 | 控制流解耦 |
| **Template Method (模板)** | 算法/流程骨架相同，局部步骤有异 | 基类或高阶函数定义执行骨架，子类/回调定制特定切片 | `ORCHESTRATE` |
| **Command (命令)** | 支持任务排队、撤销 (Undo)、重放与审计 | 将请求封装为包含 `execute()` 与 `undo()` 的独立对象 | `ORCHESTRATE` |

## 4. 模式协同集群（Pattern Cluster）与防破坏机制

### 4.1 什么是模式协同集群？
设计模式通常**由一组互相协作的方法与类构成**（例如：Context + Interface + ConcreteStrategy + Factory）。若缺乏全景记录，AI 在 VibeCoding 时很容易因“一叶障目”而直接在 Context 中加入 `if-else` 破坏模式。

因此，凡使用设计模式的业务能力，必须在 `hs_dev_docs/_03_architecture_design/_02_pattern_clusters/{cluster_name}.md` 中落盘一份**模式集群档案**（模板见 `pattern_cluster_template.md`），明确：
1. 模式角色划分（Context、Contract、Concrete、Registry）；
2. 参与方法的物理行号坐标；
3. Mermaid 协作时序图；
4. VibeCoding 防破坏硬护栏。

### 4.2 方法属性精准关联指针（Token 极度收敛）
在具体方法设计文档（`_04_engineering_contract/_04_method_design`）中，**直接打上精准模式集群指针**：

```markdown
- **模式集群关联 (patternCluster)**：
  - **集群档案**：`hs_dev_docs/_03_architecture_design/_02_pattern_clusters/billing_strategy_cluster.md`
  - **当前角色 (Role)**：`ConcreteStrategy`
  - **依从契约 (Contract)**：`IPricingStrategy.calculate`
  - **必须遵守的护栏锚点**：`#3-vibecoding-防破坏红线`
```

> **Token 节省优势**：AI 处理该方法时，通过单向指针只读取本方法定义与对应的 15 行护栏锚点，**严格禁止完整扫描或通读整个设计模式库**，将 Token 消耗控制在最低。

### 4.3 VibeCoding 防破坏三铁律
1. **禁止内联穿透**：严禁在 Context（调用方）中通过 `if-else` 跳过模式；
2. **契约不可变性**：禁止未经全局评审随意修改抽象接口参数；
3. **开闭原则闭环 (OCP)**：新增业务特性时，**必须新增具体类并在注册表中登记**，禁止修改既有具体实现类。
