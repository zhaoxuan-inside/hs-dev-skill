# 统一验收服务

所有阶段、活动及最终验收共用 `src/hs_dev/acceptance.py`，通过 CLI 调用。普通执行输出继续保留，抵达验收点时追加服务生成的统一展示。无需启动独立后台进程。

## 展示与宿主交互

固定顺序：进度导航 → 当前位置和验收范围 → 结果摘要 → 材料卡片 → 下一动作。进度仅统计任务选定范围，以有效范围确认计数；当前位置不代表已完成。材料显示稳定编号、文档链接、审阅重点、当前结果。版本、检查错误和ID映射置于折叠详情。

`acceptance TASK_ID --scope SCOPE --format markdown` 输出可读卡片；默认 JSON 提供同源数据，供宿主渲染原生复选框与按钮。Markdown 复选框是文本标记，能否点击由宿主决定。

宿主保存本次返回的 `view_digest` 及编号到材料ID的映射。用户可回答“1、3通过；2不通过，原因……”。宿主按明确反馈调用 `acceptance-decide`；同结果可批量提交，混合结果按批次记录并刷新版本，未提及项保留原状态。含糊、重名、范围不明或视图过期时先澄清，不猜测通过。

## 材料及结果

`acceptance-material` 登记实际产物的活动、相对路径、标题和审阅重点。绑定内部检查项的证据也自动进入材料目录，同活动同路径去重。证据链接不等于已人工通过。没有材料时明确显示尚无材料，不伪造文档。

| 决定 | 结果 | 交互及后续 |
|---|---|---|
| pass | 通过 | 保存实际确认原文、确认人和版本 |
| reject | 不通过 | 保存具体问题；沟通暂缓还是继续修复 |
| defer | 不通过 | 保存暂缓原因和后续动作；依赖范围继续阻断 |
| repair | 不通过 | 保存问题和修复动作；进入受影响活动，修复后复验 |

待审阅、通过、不通过、待复验和缺失分别展示。结果与处理决定分开保存。`defer`/`repair` 要求原因与下一动作。暂缓不等于NA，也不能绕过适用检查项。材料缺失不能通过。

## 版本与确认

材料决定绑定内容摘要、所属活动清单摘要和材料描述；变化后呈现待复验，原决定和历史保留。反馈必须携带当前视图摘要，旧页面反馈拒绝写入，批次中的非法ID或重复ID不会部分写入。

材料登记及反馈保存在任务 `task.json`，每次内部检查、材料或范围确认后由服务刷新派生 `acceptance.md`。恢复后用 `acceptance` 实时读取当前版本；文件快照可能滞后于外部编辑，不作为权威通过证明。任务历史 `acceptance_history` 保留每次材料决定、原文、时间与源摘要。

`approve` 是明确的范围最终确认：先验证内部清单及一致性，再将本范围尚待审阅材料随明确确认一并记通过；已有未通过、待复验或缺失材料要求先逐项解决。逐材料通过后，仍须按模式完成范围确认。stage/activity 要真实人工来源，mute 明示模型来源。

范围确认摘要同时绑定清单与材料决定；后续活动入口及任务完成均校验，不允许已拒绝材料、失效材料或旧确认通过门禁。现有全局源代次变化仍使范围确认失效，材料本身未改变的有效逐项决定保留。
