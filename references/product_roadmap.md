## 0. 为什么 MVP 范围必须在产品设计沟通时裁定？

**严禁两种反模式**：
1. **Big Bang（一次性全量研发）**：全量开发周期长、交付慢，核心假设有偏差将导致巨大浪费；
2. **先全量设计再砍半**：先把完整功能规格 + Gherkin DoD + 双轨原型 + HTML 全写一遍，再做 MVP 裁剪——被砍掉功能的规格/原型全部白做，是**结构性返工**。

因此本 Skill 把 **MVP 范围裁定前置到产品设计沟通（审讯）阶段**：先问清"只保留一个功能还能成立的那个功能是什么"，再决定写哪些详细规格。范围锁定后：
- **极速闭环验证**：MVP 聚焦单一核心假设与关键主旅程，用最小工程成本最快获得真实反馈；
- **解耦演进节奏**：全量功能解耦为梯次演进里程碑，后续选型（阶段 1）与架构（阶段 2）按当前阶段范围精准收敛，避免过度设计；
- **反返工**：详细规格、原型、Gherkin DoD 只产出一次（MVP 范围版），不再重写。

## 1. 分阶段实施的三大标准阶段

基于产品设计阶段产出的【功能架构全景树】，统一规划为三个标准化演进阶段：

| 阶段划分 | 定位与目标 | 范围特征 | 典型交付内容 |
|---|---|---|---|
| **Phase 1: MVP (核心验证期)** | 验证最核心痛点与价值闭环；极短周期交付可用版本 | **严格最小集**：仅保留核心主路径，砍掉所有非关键辅助特性 | 单一角色登录、核心业务表单提交与状态查看、极简兜底逻辑 |
| **Phase 2: 体验与增强期** | 提升操作效率、打磨交互细节、完善次级业务场景 | **体验与能力扩展**：多角色协同、高级筛选、批量导入导出、消息通知 | 运营后台、批量审核、历史版本比对、个性化配置 |
| **Phase 3: 规模化与生态期** | 业务规模化放量、开放能力与自动化赋能 | **深度与生态**：高并发调优、开放 API、自定义工作流、数据大盘 | OpenAPI、Webhooks、复杂审计大盘、第三方生态集成 |

## 2. MVP 抉择四大法则（在产品设计沟通中落地）

为杜绝"大包大揽、迟迟无法交付"的通病，本 Skill 融合 YC `gstack`、Basecamp `Shape Up` 与敏捷切片的核心方法：

### 2.1 法则一：CEO 视角质疑式裁剪（The Radical Cut · 质疑式裁剪 · 开发者最终裁定）
- **核心心智**："如果发布你的首个版本时你没感到一丝尴尬，那你就发布得太晚了"。
- **单一核心假设 (Single Risky Assumption)**：强制回答"如果本产品只保留一个功能还能成立，那个功能是什么？"。
- **质疑式提案而非直接削减 (Scrutinize Rather than Direct Cut · 开发者最终裁定)**：
  - **严禁 Agent 擅自直接砍半**：Agent 绝不越权单方面直接删除或强制剥离功能；
  - **批判性质询 (Critical Scrutiny)**：Agent 站在严苛的 CEO 视角对多角色复杂权限、运营后台、批量导出、高级复合筛选、自定义配置、站内通知等辅助功能逐一发起**必要性质疑**（例如："没有批量导出，核心闭环今天会阻塞吗？"、"没有可视化后台，直接用 SQL 种子数据能否完成首批验证？"）；
  - **整理质疑清单与替代方案**：Agent 梳理出最具争议或潜在可砍项，输出《CEO 质疑与裁剪建议清单》；
  - **开发者最终裁定 (Final Decision by Developer)**：所有功能是否砍掉、是否降级到 Phase 2/3，**完全由开发者逐项审查并最终敲定**，Agent 仅扮演批判性参谋角色；
  - **MVP 零管理台倡议 (No Admin in MVP)**：重点质询可视化配置后台，向开发者提议首期通过代码常量或 DB Migration 种子数据替代，最终由开发者签收确认。

> **⏱ 时机铁律**：以上质疑与裁定发生在**产品设计沟通（审讯）阶段，先于详细规格**（见 §3.1 的 Q1/Q2/Q3）。

### 2.2 法则二：固定时间，浮动范围（Appetite & Fixed Time · 借鉴 Shape Up）
- **团队胃口定界 (Appetite)**：在立项时明确本次 MVP 愿意投入的时间箱（如："2 天极速验证"或"1 周首发发布"）；
- **断路器原则 (Circuit Breaker)**：开发过程中若遇到工期压力，**提出范围裁剪方案并由开发者裁定；未经确认不得删减已冻结功能**；
- **No Dead Backlog**：被裁剪掉的功能不进入庞大而令人绝望的死待办池，而是待 MVP 上线并获得真实用户反馈后，再重新拉出来竞争入场。

### 2.3 法则三：垂直曳光弹切片路径 (Tracer Bullet Vertical Slice · 借鉴 Pragmatic)
- **拒绝水平切片 (Anti-Pattern)**：严禁"先做完所有表结构 -> 再写完全部后端接口 -> 最后拼装前端"的脱节做法；
- **制定 Day 1 冒烟切片 (First Vertical Slice)**：开发计划必须安排一条**贯穿当前项目实际边界的最窄端到端纵向通路**（有 UI/API/DB 才纳入对应层；无 UI 可为 CLI/库入口到真实依赖）。在开发首日或首个里程碑，就能打通最简点击提交并落库查看的链路，立刻冒烟演示。

### 2.4 法则四：MVP 依赖向开发计划编译 (MVP to Task DAG)
- 锁定的 MVP 范围直接向下游编译为**按拓扑排序的任务执行依赖图 (Task DAG)**；
- 后续阶段 1（选型）至阶段 5（实现）严格被该 DAG 锁闭，禁止任何 Phase 2/3 特性超前侵入。

## 3. 人机交互对齐机制（并入产品设计沟通 · 先于详细规格）

**Agent 严禁自作主张私自裁减 MVP 范围**！MVP 范围裁定**在产品设计沟通（审讯）阶段**完成，与产品探索追问同轮进行：

### 3.1 四项规划问题（Q1/Q2/Q3 在 0A 裁定，Q4 在 0B 定义并确认）

1. ❓ **Q1 - 单一核心假设与验证目标 (Single Risky Assumption)**：
   - 题干：本产品只保留一个功能还能成立，那个功能是什么？MVP 最核心要验证的闭环是什么？
   - ➡️ 推荐：聚焦核心主角色在单一场景下的成功路径闭环（如：完成一笔从录入到生效的主流程）。
2. ❓ **Q2 - CEO 视角功能质疑与裁剪建议 (The Radical Cut · 开发者最终裁定)**：
   - 题干：Agent 站在严苛 CEO 视角对非核心特性发起必要性质疑，提出以下【裁剪建议与质疑清单】，请开发者最终裁定：
     - *✅ 建议保留纳入 MVP (Must-have)*：[核心主旅程功能 A, B]；
     - *❓ 质疑与建议裁剪项 (Challenge & Cut to Phase 2/3)*：[次要功能 C（高级筛选）、D（批量导出）、E（可视化权限体系）、F（通知中心）]；
     - *🔍 质疑理由与极简替代*：说明缺失此功能为何不会致命、首期如何用低成本方案（如种子数据/手动配置）替代；
   - ➡️ 推荐：由开发者根据业务现实逐项裁定是否采纳裁剪建议，保持 MVP 纯粹与按期收敛。
3. ❓ **Q3 - 团队胃口与时间箱 (Appetite)**：
   - 题干：本次 MVP 期望的时间箱 (Timebox) 与交付胃口是多久？
   - ➡️ 推荐：小食规格（Small Batch: 1~3 天）或标准规格（Medium Batch: 1~2 周），严格遵循断路器原则。
4. ❓ **Q4 - 阶段首日切片与验收标准 (Tracer Bullet & DoD)**：
   - 题干：MVP 的首个垂直贯穿切片是什么？最终交付形式与 Gherkin 验收断言？
   - ➡️ 推荐：首个切片为贯通 UI+API+DB 的基础冒烟流，以可端到端跑通的核心主链路为准出条件，通过阶段 6 门禁后发布首个可用版本。

**裁定后的范围纪律**：Q1/Q2/Q3 敲定 MVP 范围后，**详细功能规格、双轨原型、Gherkin DoD 只对 MVP 范围内功能输出**（见 [`product_design.md`](product_design.md) §4）；非 MVP 功能仅登记 MoSCoW 池。

## 4. MoSCoW 优先级分级原则

在编制规划书时，所有功能点必须显式打标（无论是否入 MVP）：
- **Must-have (必须有 · 归入 Phase 1 MVP)**：没有此功能产品完全不可用，核心假设无法验证；
- **Should-have (应当有 · 优先归入 Phase 2)**：极其重要但短期可用人工或基础方式替代，不影响核心闭环；
- **Could-have (可以有 · 归入 Phase 2 或 3)**：锦上添花的功能，资源充裕时才做；
- **Won't-have (本期不做 · 归入 Phase 3 或后续规划)**：本期明确排除的非目标。

> 非 MVP 的 Should/Could/Won't **只登记到 MoSCoW 池**，不写详细规格、不做原型——这是反返工的关键纪律。

## 6. 阶段 0 冻结门禁与下游联动

《产品开发分阶段规划书》落盘、**MVP 范围经开发者裁定**、业务语义签收与冻结确认单签署，是**阶段 0 产品设计与规划整体冻结**的终极前提：

```text
[阶段 0A: 产品设计沟通] 审讯（Q1 核心假设 / Q2 CEO 质疑裁剪 / Q3 胃口）→ MVP 范围开发者裁定
        ↓
[阶段 0A': 微观特性设计] 详细规格 + 双轨原型 + Gherkin DoD（仅 MVP 范围）
        ↓
[阶段 0B: 分阶段规划] 落盘《产品开发分阶段规划书》（源自审讯结论，含 Q4 Day1 切片）
        ↓
[阶段 0C: 详细功能与规模评估] 确认当前 MVP 的功能边界、规模与 S/M/L 路径
        ↓
[阶段 0 冻结门禁] 业务语义签收 + 视觉签收 + 冻结确认单 APPROVED → 通过
        ↓
[阶段 1: 技术选型] ★ 严格按当前阶段（如 MVP）范围进行针对性选型与架构！
```

> [!IMPORTANT]
> **下游研发范围严格锁定**：
> 进入阶段 1（选型）、阶段 2（架构）及阶段 3（四要素）时，**工程任务严格限定为当前实施阶段（如 Phase 1 MVP）所划定的功能边界**！严禁为 Phase 2/3 的远期特性提前做过度工程或冗余编码。
> **DB 变更纪律**：新增业务若触达数据库设计，必须先经开发者决策（见 [`confidence_decision.md`](confidence_decision.md) §1.5），再落 V/U 迁移与编码。
