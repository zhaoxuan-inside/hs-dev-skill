# 产品分阶段实施与 MVP 规划指南 (Phased Roadmap & MVP)

**何时读**：完成全量产品设计（PRD 与设计语言）之后；进入技术选型（阶段 1）之前；规划功能分期与 MVP 裁剪时；每会话最多一次。  
**核心分工**：
- **产品分阶段规划（本文）**：定义从全量产品设计向分阶段实施演进的规则、人机交互对齐机制，指导产出《产品开发分阶段规划书》；
- **全量产品设计** → [`product_design.md`](product_design.md)；
- **审讯式人机交互** → [`grill_orchestration.md`](grill_orchestration.md) / [`confidence_decision.md`](confidence_decision.md)；

## 0. 为什么必须有 MVP 与分阶段实施？

完成全量产品设计（包含宏大的功能架构树与完整设计语言）后，**严禁直接进行全量一次性研发（Big Bang Anti-Pattern）**。原因如下：
1. **降低试错成本**：全量开发周期长、交付慢，若核心假设有偏差将导致巨大浪费；
2. **极速闭环验证**：MVP（Minimum Viable Product，最小可行产品）聚焦单一核心假设与关键主旅程，用最小工程成本以最快速度上线获得真实反馈；
3. **解耦演进节奏**：将全量功能解耦为梯次演进的里程碑，使后续技术选型（阶段 1）与架构设计（阶段 2）可以**按当前阶段范围精准收敛**，避免过度设计。

## 1. 分阶段实施的三大标准阶段

基于产品设计阶段产出的【功能架构全景树】，统一规划为三个标准化演进阶段：

| 阶段划分 | 定位与目标 | 范围特征 | 典型交付内容 |
|---|---|---|---|
| **Phase 1: MVP (核心验证期)** | 验证最核心痛点与价值闭环；极短周期交付可用版本 | **严格最小集**：仅保留核心主路径，砍掉所有非关键辅助特性 | 单一角色登录、核心业务表单提交与状态查看、极简兜底逻辑 |
| **Phase 2: 体验与增强期** | 提升操作效率、打磨交互细节、完善次级业务场景 | **体验与能力扩展**：多角色协同、高级筛选、批量导入导出、消息通知 | 运营后台、批量审核、历史版本比对、个性化配置 |
| **Phase 3: 规模化与生态期** | 业务规模化放量、开放能力与自动化赋能 | **深度与生态**：高并发调优、开放 API、自定义工作流、数据大盘 | OpenAPI、Webhooks、复杂审计大盘、第三方生态集成 |

## 2. 强制人机交互对齐机制 (Human-in-the-Loop Alignment)

Agent **严禁自作主张私自裁减 MVP 范围**！从“全量产品设计”切入“分阶段规划”时，**必须暂停并主动触发一轮人机交互对齐（Grilling）**，向人类决策者提出结构化问题并提供推荐方案：

### 2.1 人机交互三必问（结构化题单）

1. ❓ **Q1 - MVP 核心价值与验证目标**：
   - 题干：本次 MVP 阶段最核心要验证的用户痛点和核心业务假设是什么？
   - ➡️ 推荐：聚焦于核心主角色在单一场景下的成功路径闭环（如：完成一笔从录入到生效的主流程）。
2. ❓ **Q2 - 功能范围裁剪与 MoSCoW 分级**：
   - 题干：基于功能架构树，以下特性推荐列入 MVP (Must-have)，其余特性推荐移入 Phase 2/3 (Won't-have in MVP)，请确认或调整裁剪边界：
     - *建议 MVP 包含*：[核心主旅程功能 A, B]；
     - *建议暂缓/裁减*：[次要功能 C（高级筛选）、D（批量导出）、E（权限体系）]；
   - ➡️ 推荐：采纳推荐裁剪方案，保持 MVP 高度纯粹。
3. ❓ **Q3 - 阶段里程碑与验收标准**：
   - 题干：MVP 阶段的交付形式与核心验收断言是什么？
   - ➡️ 推荐：以可端到端跑通的核心主链路为准出条件，通过阶段 6 门禁后发布首个可用版本。

用户确认或答复后，将对齐结论形成记录，正式编写规划书。

## 3. MoSCoW 优先级分级原则

在编制规划书时，所有在 PRD 中定义的功能点必须显式打标：
- **Must-have (必须有 · 归入 Phase 1 MVP)**：没有此功能产品完全不可用，核心假设无法验证；
- **Should-have (应当有 · 优先归入 Phase 2)**：极其重要但短期可用人工或基础方式替代，不影响核心闭环；
- **Could-have (可以有 · 归入 Phase 2 或 3)**：锦上添花的功能，资源充裕时才做；
- **Won't-have (本期不做 · 归入 Phase 3 或后续规划)**：本期明确排除的非目标。

## 5. 阶段 0 冻结门禁与下游联动

《产品开发分阶段规划书》落盘并通过人机交互确认，是**阶段 0 产品设计与规划整体冻结**的终极前提：

```text
[阶段 0A: 产品设计] PRD 功能规格 + 设计语言原型
       ↓
[人机交互对齐] Q1 核心假设 / Q2 范围裁剪 / Q3 里程碑
       ↓
[阶段 0B: 分阶段规划] 落盘《产品开发分阶段规划书》
       ↓
[阶段 0 整体冻结门禁] 通过
       ↓
[阶段 1: 技术选型] ★ 严格按当前阶段（如 MVP）范围进行针对性选型与架构！
```

> [!IMPORTANT]
> **下游研发范围严格锁定**：
> 进入阶段 1（选型）、阶段 2（架构）及阶段 3（四要素）时，**工程任务严格限定为当前实施阶段（如 Phase 1 MVP）所划定的功能边界**！严禁为 Phase 2/3 的远期特性提前做过度工程或冗余编码。
