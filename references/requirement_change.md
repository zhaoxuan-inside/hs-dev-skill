# 需求变更通道（Requirement Change）— 冻结后的变更治理

**何时读**：阶段 0 已冻结后出现需求变更、范围增减、推翻已冻结结论、或实现期新暴露的产品空白时；每变更一次走一遍。  
**分工**：执行层断点/回退 → [`process_continuity.md`](process_continuity.md)；回切 DESIGN 审讯 → [`grill_orchestration.md`](grill_orchestration.md)；DB/契约决策 → [`confidence_decision.md`](confidence_decision.md) §1.5。

---

## 0. 原则

**冻结不是「禁止变更」，而是「变更必须走显式通道」**。需求必然演化，禁止 Agent 静默改、静默加、静默砍——每个变更都要有影响评估与开发者确认，否则冻结文档与实现漂移，返工无从追责。

---

## 1. 变更请求单（Change Request，必填字段）

| 字段 | 说明 |
|------|------|
| `CR-{task_id}-{n}` | 变更编号 |
| 变更描述 | 改什么 / 为什么改 / 谁提出 |
| 触发来源 | 开发者 / 测试暴露 / 外部反馈 / 实现期发现 |
| 影响面 | PRD · 原型 · 选型 ADR · 架构 · DB Schema/迁移 · API 契约 · 已实现代码 · 测试 |
| 返工代价评估 | 需重写的文档/代码范围、回滚风险、工期影响 |
| 建议方案 | Agent 推荐做法 + 备选（可逆优先） |
| 开发者裁定 | APPROVED / REJECTED / 修订 |

落盘：`hs_dev_docs/_06_dev_process/_03_qa_log/{task_id}_cr.md`（与 Q&A 日志同目录，便于回溯）。

---

## 2. 流程（R1～R5）

```text
R1  发现变更（用户提出 / 实现期暴露产品空白 / 测试失败揭示语义冲突）→ 暂停当前推进
R2  填写《变更请求单》：影响面 + 返工代价评估 + 建议方案
R3  分类处置：
    · 触产品语义 / 对外契约 / DB / 架构边界 → 回切 DESIGN（迷你审讯），并把变更请求单并入审讯
    · 纯工程可逆项（命名/内部拆分/日志）→ 记一行假设后直接执行
R4  开发者确认裁定（DB 与不可逆契约变更：必须开发者决策，禁止跳过）
R5  更新冻结文档 + plan_log/change_log；按新冻结继续推进
```

**DB 变更硬规则**：**新增业务/新功能凡是需要改动数据库设计（新增表、改表结构、破坏性迁移、不可逆字段），必须经开发者决策确认后才能落 V/U 迁移脚本与编码**。此规则**不受**实现期四条件闸门（置信度自决）约束，也不属于可跳过项（见 [`confidence_decision.md`](confidence_decision.md) §1.5 禁止跳过清单）。

---

## 3. 与 process_continuity 的关系

- `plan_log` / `change_log` 负责**执行层**的断点、续做、回退；本文负责**需求层**的变更治理。  
- 变更确认后：先 `process_log.py checkpoint` 记录变更前状态，再落变更，保证可回退。
