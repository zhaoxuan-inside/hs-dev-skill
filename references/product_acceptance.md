# 需求与产品设计验收清单

**何时读**：新需求理解、阶段 0 产品设计、场景演练、冻结或业务变更；只读当前节。
**执行**：按 [阶段验收协议](stage_acceptance.md) 实例化检查表。下列各行都是验收项，默认 PENDING，不能直接勾为通过。

## 1. 先取证，再设计

先采集开发者的真实案例与现有流程，再复述预期、暴露歧义，随后比较方案。不要用预填的抽屉、表格、管理员、色彩等模板内容替代需求。

每个重要结论区分：`CONFIRMED`（开发者明确确认）、`DERIVED`（Agent 推导，附依据）、`OPEN`（未决）。DERIVED 不因写入 PRD 自动成为 CONFIRMED。对业务预期有影响的推导须明确确认。

维护“开发者表达 → Agent 理解 → 场景预期 → 确认记录”的对账表。一个布局选择的确认不代表确认隐含业务规则。先验证操作方式，再细化视觉。

## 2. 0A 需求理解与范围

输入：原始请求、已有资料及现状证据。产出：对账表、范围、假设与未决项；这些可直接放入 PRD 前部或开场对齐记录。
依据：NASA C.2～C.4、GOV.UK 用户需求指南；具体门禁为本 Skill 自定规则。

| ID | 工作 todolist | 验收标准与所需证据 |
|---|---|---|
| DISC-01 | 还原真实使用案例 | 核心角色、触发情境、现有动作、实际困难及预期结果齐全；每项有开发者陈述/现状资料来源，缺少实际用户证据须说明 |
| DISC-02 | 复述目标与反目标 | 明确本期做/不做、需要保留的行为、不可接受的结果；开发者确认范围，不能自行删减必要闭环 |
| DISC-03 | 对齐术语与关键动词 | 创建、保存、提交、生效、撤销等在本项目的含义明确；批量/逐条、自动/人工、同步/异步等高返工歧义有裁决与例子 |
| DISC-04 | 盘点角色和约束 | 谁操作、谁审批、谁拥有数据/付费、谁验收明确；适用的平台、现有系统、预算和时限记录为约束，未知项有处理计划 |
| DISC-05 | 暴露假设与理解差异 | 每个影响业务/结构的 DERIVED 或 OPEN 项逐项确认或关闭；无“用户没反对所以默认认可” |
| DISC-06 | 确定最小闭环 | 入口、必要步骤、输出及完成判据可以贯通；范围裁剪附损失与替代方案，经开发者确认；不以普遍 MVP 口号排除实际必需功能 |
| DISC-07 | 核对成功与失败例子 | 每个核心目标至少有具体输入、动作、可观察结果；适用的反例/边界例已写出，能区分两种可能理解 |
| DISC-08 | 提交理解验收 | 对账表有来源、场景 ID、明确确认范围及未决项；开发者核对后 ACCEPTED，才能展开依赖这些结论的详细设计 |

阻断：没有核心真实案例、范围未确认、关键操作语义仍有两解、Agent 假设伪装为已确认结论。

## 3. 0B 产品设计与冻结

输入：已验收的 0A 基线。产出：PRD、需求/规则/场景清单、适用的原型与 Vibe Spec、冻结确认单。
依据：GOV.UK Alpha 原型验证、NASA 需求质量检查；ISO 9241-210/29148 仅用公开范围定位，未声称逐条符合。

| ID | 工作 todolist | 验收标准与所需证据 |
|---|---|---|
| PROD-01 | 原子化需求 | 每个 REQ 有唯一 ID、来源目标、适用角色/条件、要求和可观察结果；拆开独立义务，避免“灵活、快速、完善”等无判据措辞 |
| PROD-02 | 定义完整业务流程 | 每个核心场景从进入到完成有步骤、决策点、角色交接及中断后的去向；覆盖实际批量/离线/跨会话操作，不只画页面跳转 |
| PROD-03 | 定义规则与状态 | 适用的前置条件、默认值、边界、优先级、权限、状态迁移/禁止迁移明确；冲突有裁决，涉及归属/计费不能靠 Agent 猜测 |
| PROD-04 | 定义失败与恢复结果 | 适用的校验失败、无权限、无数据、超时、重复操作、部分成功有用户结果与数据结果；能说明如何重试、恢复或终止 |
| PROD-05 | 编写行为验收场景 | 每个必需 REQ 映射 Given/When/Then；Then 包含业务结果及必要持久化效果，不能仅断言 Toast、按钮或 HTTP 成功 |
| PROD-06 | 用任务演练核对原型 | 开发者拿真实样例走完核心任务与关键例外；记录输入、路径、预期、观察到的差异和裁决。截图/视觉签收不能替代流程核对 |
| PROD-07 | 核对界面表达 | 有 UI 时核对目标终端、信息层级、关键操作及适用的加载/空/正常/错误状态；视觉与既有设计语言一致，遵守原型签收规范；无 UI 可 NA |
| PROD-08 | 定义适用质量约束 | 对本项目重要的响应、容量、可访问性、隐私、可靠性等有场景、约束值/可判定标准及验证方式；不照搬默认时间阈值，不强迫所有维度 |
| PROD-09 | 对账所有设计视图 | 已验收范围 ↔ REQ ↔ 规则/场景 ↔ 原型/Vibe Spec 对应；无孤立功能、漏项或相互矛盾的字段和状态；派生视图绑定源版本 |
| PROD-10 | 关闭高风险可行性问题 | 对可能推翻产品承诺的外部能力/平台限制有现有证据或限时探查结论；未知关键能力不能以“后续选型再看”通过冻结 |
| PROD-11 | 提交冻结验收 | 0A 与 PROD 项有证据；开发者对指定版本的范围、业务场景、关键规则及适用视觉签收；未决阻断项为零 |

阶段 0 内允许为 PROD-10 做有边界的能力探查/实验，记录问题、环境、结果与产品影响；不提前锁定完整技术栈、不发布、不擅自执行付费或破坏性操作。实现细节放独立证据，PRD 只保留约束与结论。

产品阶段确认是否需要持久化及其业务归属/保留/删除规则。物理 DB 设计在阶段 3 验收，不要求阶段 0 提前完成 DDL；已有 DB 决策引用原记录。

## 4. 场景与预期对账样式

| 开发者表达及来源 | Agent 理解 | 场景与预期结果 | 差异/裁决 | 确认范围与记录 |
|---|---|---|---|---|
| “同一笔操作不能重复生效”（来源位置） | 网络超时重试也应受约束，待确认 | 同一业务请求重试：只形成一笔业务记录，能获知原处理结果 | 明确重复判定范围与有效期 | PENDING，等待对该场景的明确确认 |

按钮短时禁用仅是交互措施，不能替代重复生效的业务保证。此例只演示拆解方法，不默认给所有项目增加幂等需求。

## 5. 反例检查

- “功能完善，界面友好”没有操作和结果，不能验收。
- “提交后显示成功”未说明何时真正生效，不能证明业务闭环。
- “选择方案 A”只确认已展示的 A；未展示的规则仍需对账。
- “无未决项”必须能追溯每个原问题的处理，不接受删除问题获得清零。
