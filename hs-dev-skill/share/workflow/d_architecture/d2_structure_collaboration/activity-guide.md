# D2 结构与协作设计

## 目的与适用范围

将本次职责边界落实为清晰的依赖、运行协作及必要部署关系。只展开受影响模块、进程和外部边界，复用有效结构；不为完整视图扩大成全系统架构重建或基础设施建设。

## 输入与输出

输入为有效职责和信息所有权、业务场景、技术约束及相关实际导入、调用和启动配置。输出包含依赖方向、接口责任、代表运行过程及适用部署条件，附依据与未知。新设计与现状分别标明，不把建议图当作已存在实现；可用文字、表或图，不强制三类图全部出现。

## 工作与核验

1. 核对模块及外部适配边界，沿实际或拟定接口检查依赖方向和责任；区分逻辑依赖、运行调用与部署关系，检查循环和实现细节泄漏。核心业务不依赖测试替身或可选追踪，不能因此破坏项目明确的其他业务日志/审计契约。
2. 选择本次代表成功和风险相关失败场景，追踪入口、调用、业务信息、状态及结果；只在涉及时展开线程、进程、后台任务或消息协作，不默认增加队列和服务。
3. 对相关协作说明同步/异步、资源所有者、开始/结束及失败传播边界；具体超时、重试、事务和恢复规则需要细化时交 E4，业务结果缺失交产品过程，不在图中擅自补齐。
4. 涉及部署或启动变化时，说明实际单元、环境配置、启动/停止及外部依赖条件；逻辑模块可以同进程部署，不将每个模块机械拆服务。缺失配置或外部能力按证据说明，不自动创建资源。
5. 对照职责和有效场景核验结构及协作，与相关框架、后端/前端及 testing 共享必要证据。静态走查、模拟和实际运行分别记录，展示取舍、未知及影响并依当前模式确认。

## 边界与交接

本活动不替代物理数据/API 契约、详细失败机制或业务规则设计，不自动安装、部署、迁移和重构。实际运行检查须在授权范围，纯设计可交付核验计划但不能宣称已部署可用。关键接口责任或协作语义未定时保持依赖阻断；适用标准及确认满足后按具体缺口转 D3、D4 或工程契约设计，不全量展开后续活动。
