# D1 领域与职责划分

## 目的与适用范围

为本次相关业务概念、规则和信息确定清晰职责及模块边界。新设计从有效业务契约出发，存量调整同时核对实际代码；局部问题只检查受影响边界，不默认重建全部领域模型。

## 输入与输出

输入为有效业务规则、术语、业务边界、质量/技术决定及相关工程现状。输出包含相关概念含义、职责和信息所有权映射、模块边界及公开契约原则，附取舍与未决项。复用既有词典和设计，不另建竞争性定义；产品含义未定时返回负责过程，不用技术命名代替业务决定。

## 工作与核验

1. 从本次场景核对术语、实体和规则，区分业务概念与表、类或文件等技术表达；记录文档与代码冲突，不能将代码现状自动当作正确需求。
2. 沿操作及信息读写链确定规则执行、权威数据、变更及派生副本的责任；说明外部主体边界，检查遗漏和多个权威来源。共享读取不等于共同拥有，集中存储不等于同一业务职责。
3. 按共同变化原因和不变量组织职责，说明边界内聚、跨边界契约及应隐藏的细节。避免因相似代码、目录或模式名称机械合并/拆分；按需由框架、后端或相关专业技能核对。
4. 只有领域复杂度需要时采用 DDD，说明其解决的问题与成本；简单场景用更轻结构。逻辑模块不自动变成微服务、独立进程或独立数据库，部署与协作由 D2 承接。
5. 用代表业务场景及变化例子核验术语、责任和边界，关联实际代码或设计位置；静态设计审阅与实现验证分别记录。展示取舍、冲突和未知，并按当前模式确认。

## 边界与交接

本活动不擅自修改业务行为、决定物理 Schema 或 API 细节，也不自动拆服务、迁移数据或重构代码。关键含义或归属未明确时保持依赖阻断；非阻断未知说明条件及下一动作。适用标准与确认满足后按具体缺口转 D2 或工程契约设计，不把模块划分文档当作实现正确或运行隔离已获证明。
