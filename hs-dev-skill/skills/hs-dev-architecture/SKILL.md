# D 架构设计

给实施者足够清楚的责任与依赖边界，同时保留局部实现选择空间。

与用户问答及展示方案时，先遵循[统一表达规范](../../references/questioning.md#面向用户的表达)。

## 进入与活动选择

先核实当前诉求与已有有效成果，仅补当前缺口。按下列活动选择当前对象；不明位置时才查[活动索引](../../references/activities.md)，不加载整个catalog或阶段正文。使用公开命令 `template --activity ID [--output ID]` 只取得当前活动或输出的具体问题、证据与通过标准。模板留空、来源缺失或最坏情况未处理不能作为已完成。

## 必要输入

- 当前业务规则、质量标准、技术决定和既有架构。
- 实际模块、代码入口、数据读写、调用与部署关系，以及验证和演进约束。

## 本阶段的判断重点

- 沿业务事件和信息生命周期划分谁持有权威数据、谁执行规则、谁承担失败；不按目录机械拆模块。
- 区分逻辑依赖、运行协作和部署单元；只有实际需要才增加进程、服务或基础设施。
- 用变化与故障场景检查质量机制、测试接缝、兼容及恢复责任。
- 让实际负责消费、提供、运行和维护边界的角色独立审查，并对所有权或失败传播冲突交叉质疑。

## 最低达成标准

- 职责、所有权、依赖方向和公开契约可定位，代表场景没有无人负责的状态。
- 机制关联质量目标、成本和验证；目录及资料单源约定支持开发者定位规则、实现与测试。

## 执行与交接

完整执行[共同工作循环](../../references/cycle.md)，不另设本阶段的锁、授权或提交流程。查证与阅读遵循[信息规范](../../references/information.md)，主动追问、回答后反例与独立多角色讨论遵循[讨论规范](../../references/questioning.md)。

现行职责、依赖、工程组织与设计决定维护在 `hs-dev/project/`；本次架构变更、兼容和演进条件进入 `hs-dev/deliveries/`，核验证据由程序保存。

不能从图和模式名称推定运行保证；关键所有权或协作冲突未解决时暂停相关详细设计，不擅自迁移系统。
