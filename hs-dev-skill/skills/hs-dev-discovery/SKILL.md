# 需求与产品设计

从用户目标和已有产品决定中找出本次缺口，只展开受影响功能。已有边界和行为直接复用；完整新产品可以逐步覆盖多个活动，但不预读 A、B 全部资料。产品结果明确后才按当前诉求切换设计或规划。

## 执行清单

- [ ] **建立发现基线**：明确当前诉求、目标对象、本轮范围、有效产品决定及实际缺口。区分用户要求、现状事实、假设、建议与冲突；工程可查信息先核实，不反复询问已有有效决定，不把现有代码行为自动当作期望。
- [ ] **选择活动与专业协作**：按下表选择受影响活动，由 product 提供专业分析，前端协助交互与平台可行性，相关工程技能核实技术约束。过程负责组织决定和依赖，不复制领域工作方法；技术限制须有证据，不能未经裁决据此删除产品需求。
- [ ] **组织必要澄清**：优先提出会改变范围、可见行为或后续依赖的问题，说明待决定内容及选项差别；不把所有问题一次性倾倒给用户。必要答案未到时暂停依赖动作，继续独立工作；不以建议、默认值、沉默或等待时长代替决定。
- [ ] **形成可追溯结果**：关联需求来源与已有功能标识，分别记录已决定、待定、排除及新增建议，说明适用范围和依据。新反馈改变有效决定时，由 continuity 协同核对影响和相关失效，不全量推翻成果，也不静默扩充功能或缩减需求分母。
- [ ] **核验并确认**：依适用标准检查场景、角色、边界、状态、异常及跨功能一致性，区分文档审阅、原型演练和真实用户证据。展示具体结果、风险及待决问题，按当前模式和统一协议处理确认，不代签、不重复确认仍有效决定。只读咨询不写入任务或确认状态。
- [ ] **结束或转交**：本次范围、预期行为、必要角色及关键依赖可判断，阻断性决定已解决后，按当前诉求转入设计或规划；仍有阻断时明确影响、缺失决定和下一动作，不能宣称已准备就绪。非阻断未决项标明条件和处理路径；局部澄清不等于整产品设计完成，不自动实施或发布。

## 输出与边界

交付当前活动所需的产品结果、决定来源、检查证据、未决项及下一动作；简单问题可直接回复，不强制新建产品文档或调研任务。专业方法复用 product，技术契约交由工程设计；市场或用户结论须有对应证据，不从建议推导“已验证需求”。
