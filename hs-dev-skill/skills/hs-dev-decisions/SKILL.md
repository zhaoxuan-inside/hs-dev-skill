# C 质量与决定

明确什么质量必须达到、哪些保证可依赖，以及为什么选定当前方案。

与用户问答及展示方案时，先遵循[统一表达规范](../../references/questioning.md#面向用户的表达)。

## 进入与活动选择

先核实当前诉求与已有有效成果，仅补当前缺口。按下列活动选择当前对象；不明位置时才查[活动索引](../../references/activities.md)，不加载整个catalog或阶段正文。使用公开命令 `template --activity ID [--output ID]` 只取得当前活动或输出的具体问题、证据与通过标准。模板留空、来源缺失或最坏情况未处理不能作为已完成。

## 必要输入

- 有效业务场景、质量诉求、运行规模和必须保持的行为。
- 实际平台与依赖版本、环境、成本或资源限制及现有方案证据。

## 本阶段的判断重点

- 将“快、稳定、安全”等诉求转为对象、条件、响应和判据；规模估算写明来源与假设。
- 先检查现状能否满足目标；必要时在相同条件下比较候选及运行、迁移和维护代价。
- 可能推翻决定的保证先核实，必要时做最小实验；真实失败不被模拟成功覆盖。
- 产品价值、维护、运行与安全等实际责任者存在取舍时独立分析并相互质疑；不按技术名词堆角色。

## 最低达成标准

- 每个关键目标有可执行或可重复的验证方法、环境与通过条件。
- 决定关联依据、候选/被否方案、适用版本、影响对象和剩余风险，建议与已定方案分开。

## 执行与交接

完整执行[共同工作循环](../../references/cycle.md)，不另设本阶段的锁、授权或提交流程。查证与阅读遵循[信息规范](../../references/information.md)，主动追问、回答后反例与独立多角色讨论遵循[讨论规范](../../references/questioning.md)。

现行质量标准与有效决定入口维护在 `hs-dev/project/`；本次选型、实验目的和适用结论进入 `hs-dev/deliveries/`，真实实验记录由程序保存。

关键平台保证、配额或成本未知时，不承诺方案可行；未获授权的风险接受不能由模型代签。
