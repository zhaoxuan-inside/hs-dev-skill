# A 产品意图

形成有来源的问题与目标，使后续设计知道为什么做、为谁做以及不承担什么。

与用户问答及展示方案时，先遵循[统一表达规范](../../references/questioning.md#面向用户的表达)。

## 进入与活动选择

先核实当前诉求与已有有效成果，仅补当前缺口。按下列活动选择当前对象；不明位置时才查[活动索引](../../references/activities.md)，不加载整个catalog或阶段正文。使用公开命令 `template --activity ID [--output ID]` 只取得当前活动或输出的具体问题、证据与通过标准。模板留空、来源缺失或最坏情况未处理不能作为已完成。

<!-- hs-activity-nav:A:start -->
- `A1` 问题、愿景与价值
- `A2` 定位与产品调性
- `A3` 核心能力与业务边界
<!-- hs-activity-nav:A:end -->

## 必要输入

- 用户目标、真实事件与当前做法；已有产品决定、实际资料及其来源。
- 相关角色、业务对象、外部主体、现有能力与约束；缺失内容保持未知。

## 本阶段的判断重点

- 不要直接接受功能愿望：追问实际触发、现有步骤、损失与原因，再检验提出的方案。
- 从使用者与承担交接、支持或风险的角色组织独立分析，找出责任空缺与冲突。
- 定位与价值主张有事实或明确假设支撑；代表场景可判断成功与未成功。

## 最低达成标准

- 用户、场景、问题证据与关键假设分开；目标、排除范围和成功标准可解释。
- 能力及业务责任覆盖当前对象生命周期；关键未知说明影响、验证方法和下一动作。

## 执行与交接

完整执行[共同工作循环](../../references/cycle.md)，不另设本阶段的锁、授权或提交流程。查证与阅读遵循[信息规范](../../references/information.md)，主动追问、回答后反例与独立多角色讨论遵循[讨论规范](../../references/questioning.md)。

当前问题、目标、定位和业务边界维护在 `hs-dev/project/`；本次调查的范围与结论进入 `hs-dev/deliveries/`，实际来源与讨论记录由程序关联。

问题或价值假设尚未成立时，不以赞同方案冒充需求验证；只阻断消费该假设的设计，继续独立调查。
