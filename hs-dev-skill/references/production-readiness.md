# 生产开发与上线证据

当任务涉及生产服务、新后端、权限、数据迁移、部署或生产就绪判断时读取；普通局部修改只处理受影响项。沿用当前项目的质量标准和有效证据，把结果填入已有 C/E/G/R/H 活动产出，不增加阶段、固定文档或审批。

## 开发前确定要兑现的保证

先定位本次支持的部署形态、真实依赖和版本、数据规模、兼容边界以及允许的外部作用。把“能运行”细化为本次可观察的业务与质量结果；没有容量、延迟或恢复目标时不能自行编造达标数字。目标未定只阻断依赖它的接受判断，已有授权内的调查和修复继续。

对每条关键保证，能找到：权威规则、负责实现、实际消费者、验证入口、结果及所测版本/环境。重点复核以下适用边界：

- **授权与数据生命周期**：租户、用途、撤回、删除、缓存、历史页与派生结果；按[跨边界审查](engineering-review.md)检查取得后失效再消费。
- **持久化与并发**：每个声明支持的后端使用真实组件验证事务、锁顺序、重入、幂等与失败回滚；单后端或串行用例不能支持其他后端和并发保证。
- **故障与运行**：按本次风险验证依赖不可用、重启、取消、超时、有限重试和资源清理；确认日志、错误响应、指标与探针能识别实际失败，并核对敏感内容是否残留。验证命令自行管理其创建的容器、服务与临时资源。
- **升级与恢复**：有存量数据或格式变化时，使用隔离的代表性旧版本数据验证升级及失败后的恢复；保留数据兼容条件，不能把恢复代码前像等同恢复数据库、密钥或外部副作用。
- **交付路径**：使用实际包/镜像在声明的条件下安装、配置、启动并完成核心任务；支持矩阵、密钥来源、最小权限、备份及容量检查按实际用途取证。源码测试与打包成功不能代替安装后验证。

关键规则的验证要有独立来源：从原始要求推导反例，再对照实现与用例，避免实现和测试共用同一个错误假设。需要独立角色而当前不能委派时标明单 Agent 审查限制；不伪造独立审查记录。

## 验证如何支持接受

保留命令、版本/配置、实际环境、通过/失败/跳过数量及证据位置。退出码 0 后还要核对测试是否收集、必要后端/模型是否真正调用、跳过项是否影响关键保证；Mock、干运行、历史报告与真实集成分别标明。失败后的修订保留原失败，只复验受影响保证与必要回归；最终接受证据绑定最终产物。

把未覆盖项写清影响、责任归属和首个下一动作。关键保证失败、缺证据或存在未决高影响异议时，阻断相应上线判断；不能用大量其他通过项抵消。非阻断剩余项也须有接受该风险的真实依据，模型不能代替负责人签收。

交付结论明确当前达到了哪一步：代码完成、隔离集成通过、目标环境验收通过、已部署。用户只要求开发时，继续完成可验证的代码与交付准备；缺少生产访问或上线授权不等于停止所有开发，也不能据此宣称已上线。发布、生产迁移和真实恢复沿用实际授权边界。

## 执行工具的适用边界

本工具协调受管文件与证据，运行验证命令时使用执行者的权限。POSIX 同进程组残留会被清理并拒绝通过，但独立 session、容器、远端任务等不能由此保证终止；检查入口须自行管理生命周期。执行锁不是系统级文件锁，内容摘要不覆盖权限、属主、ACL 或扩展属性，不能用一致性提交证明这些元数据或外部资源已恢复。

原子替换保留已有文件的 POSIX mode，新取得的前像记录 mode 供删除后恢复。旧交付没有 mode 快照时无法还原被删文件的原权限；涉及该情况须另行核验后再接受。ACL、属主、扩展属性和断电持久性未提供完整恢复保证。有这些要求时使用项目原生、已验证的部署/恢复机制。
