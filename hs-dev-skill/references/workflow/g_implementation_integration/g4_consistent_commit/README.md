# G4 一致性提交

## 目的与适用范围

将本次受管变更发布为可核验一致修订，保护源、索引及证据的版本关系。具体顺序和权限以[执行协议](../../../core/execution.md)为准，本活动核验结果，不另造提交、锁或恢复流程。只读分析不执行发布。

## 输入与输出

输入为当前任务/活动、操作归属、实际修改集合、恢复依据和对应内容摘要的验证证据。输出为发布及一致性结果、活动归属、证据/确认状态和未解决项。受管提交不自动产生 Git commit，也不授权 push、部署或发布应用。

## 工作与核验

1. 核实当前操作、UUID/fence、授权范围、任务活动及有效上游，检查已有修改和恢复覆盖；不手工改 SAFE 或通过新操作掩盖未完成状态。
2. 使用现有 commit 或受管外部编辑/reconcile 路径，按执行协议处理快照、修改登记及真实验证。两条路径细节不同，不以活动清单重新规定一套底层步骤或直接调用内部函数绕过协调。
3. 核对验证所覆盖的源摘要和实际修改一致；验证后或发布期间相关内容变化时证据需复核，不能强行发布。G2/G3 有效结果可复用，但不把旧修订证据冒充当前验证。
4. 核验索引发布及相关缓存状态、活动输出归属和确认失效处理，复核实际依赖；索引是派生物，重建本身不改变业务源，也不一概撤销无关有效确认。框架应用自身缓存仅在本次修改涉及其契约时另行验证。
5. 中断时保留真实操作及恢复依据，按 continuity 和[恢复协议](../../../support/recovery.md)处理继续/回滚。撤销凭据不恢复文件，命令失败不等于必须回滚；快照不可用或后续编辑冲突保持阻断，不扩大回滚范围覆盖其他工作。
6. 发布后核对源摘要、发布状态和必要证据/确认仍有效，再按协调结果报告安全与完成。安全、操作发布、任务完成及人工验收分别判断，展示未验证项和下一动作，不把一次命令成功当作全部完成。

## 边界与交接

本活动不自动执行破坏性中断演练、恢复或清理，计划和静态依据不能记作恢复验证成功。未验证或漂移状态不得标安全；范围内结果有效后按当前模式处理确认，并依诉求进入交付核验或下一任务，不自动提交 Git、发布应用或重走完整流程。
