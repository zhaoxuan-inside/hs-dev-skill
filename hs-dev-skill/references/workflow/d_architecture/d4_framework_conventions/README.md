# D4 框架与目录约定

## 目的与适用范围

将本次已选框架和架构决定落实为可维护的代码/资源组织及文档约定。沿用项目现有合理结构，只处理实际缺口；不把工作流自身的阶段目录布局强加给业务项目。

## 输入与输出

输入为相关职责、协作、质量机制、技术决定及实际框架版本、目录和构建/打包约定。输出说明本次适用的资源职责、装配边界、命名/抽象原则、文档定位及契约单源规则，附检查结果和例外。没有全局规范时只形成当前范围一致的局部约定，不宣称已建立全项目标准。

## 工作与核验

1. 核实实际框架和工具链版本、入口、构建配置及邻近代码约定；涉及框架机制时查证适用版本，不从候选名称推定项目采用方式，也不借目录调整重新选型。
2. 按职责区分业务实现、运行配置、测试、测试数据及适用替身，核对装配和正式产物边界。框架支持的共置测试不必迁目录；没有外部替代需求不创建独立 Mock 服务，正式业务不得依赖测试夹具或模拟兜底。
3. 用本次变化场景检查目录与命名能否表达职责，抽象是否有稳定契约或独立变化依据。业务常量应有清楚语义，不机械提取所有数字和字符串，也不为模式增加层级。
4. 按真实读者和维护需要选择文档入口与形式，优先更新现有资料；阶段/活动 README 是本工作流的组织方式，不是所有工程的交付要求。表格和 Mermaid 只在更清楚时使用，不强制生成。
5. 明确机器契约的权威来源及派生关系，变更时同步生成源和必要产物，核验链接与相关构建/打包规则。区分静态检查、实际命令和计划，展示例外、未知及影响并按当前模式确认。

## 边界与交接

本活动不自动移动文件、重构代码、修改 Agent 配置或引入 CI/CD；具体变更沿当前授权和执行协议处理。关键装配或契约来源冲突未解决时保持依赖阻断，非阻断例外保留理由与后续条件。适用标准及确认满足后按具体缺口转工程设计或实施，不以目录齐全或构建通过证明业务正确。
