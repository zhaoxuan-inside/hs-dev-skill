# 讨论与提问

先调查与思考，再带着具体判断沟通。目标是形成开发依据、揭示取舍和消除关键歧义，不是收集赞同或把问题全部交给用户。

## 面向用户的表达

与用户问答时，明确展示以下三个部分，默认每部分一两句：

1. **用户问题理解**：用用户的语言说清要解决什么，包含本轮纠正；不复述整段历史。
2. **原因分析**：说明关键原因及影响；推测明确标记，不堆叠内部状态、术语或未经验证的结论。
3. **答案或建议方案**：能直接回答就回答；需要取舍时给具体选项、主要代价和建议。只有答案会改变必要决定时才提问。

简短问答也保留三项，每项一句即可；原因尚未核实时直说，不为凑格式编造原因。进度更新只说新发现、影响和正在执行的动作，不必重述三项，也不把整份执行记录搬给用户。用户不需要知道的交付ID、摘要、命令和阶段编号留在证据里。用熟悉的词解释结果和影响；避免长清单、重复边界声明、机械道歉和“将会继续”的空承诺。用户需要比较或作复杂决定时再展开。

**方案与实现分开**：方案先讲目标、预期行为、取舍和验收，不夹带文件、代码和命令；实施计划另讲怎么改、怎么测和如何恢复；完成后单独报告实际结果。较复杂的方案和实施记录用独立文档相互引用，小改动可分段，无须为凑形式新增文件。顺序不等于审批，已有授权覆盖的工作直接继续。

发送前检查：三项是否清楚？能否删去重复句而不丢信息？用户能否不读实现细节就理解方案？不能以文档结构合规代替这三项阅读检查。

## 问题的影响范围

提出问题前，说明答案具体影响哪些工作。真正决定当前活动能否继续的问题默认阻断；仅为后续验收收集样本等补充问题，登记不阻断当前活动的原因和实际影响范围，继续独立工作。补充问题不意味着其依赖范围已获放行；进入该范围时必须重新评估，不能把它永久降为可选项。

用户否定问题前提或撤回问题时，保留问题及真实决定来源，用 `question-resolve` 记录 `invalid-premise` 或 `withdrawn`；这不是用户接受方案，也不是补造回答。工程师自己发现提问多余时先重新分析依赖；无真实决定来源不能用该接口清除业务阻断。旧问题默认仍阻断，不能静默改状态。

## 何时组织真实多角色讨论

新产品、多种利益相关角色、关键业务规则冲突或错误决定会引发大范围返工时，组织独立 Agent 讨论。局部且规则明确的变更复用既有认识，仅核实新差异，不为每次修改启动整场讨论。

1. **选角色**：从实际使用者、管理者、运营/支持者、外部合作方及承担风险者中选择相关角色；技术实施者提供可行性检查。只选会改变本次判断的角色，不固定凑人数或虚构角色证据。
2. **独立分析**：实际委派不同 Agent，各自只取得共同事实、当前问题和必要材料，不先给协调者的倾向性答案。每个角色给出自身任务、成功条件、失败后果、隐藏假设、冲突和最想核实的问题。
3. **交叉质疑**：交换有依据的分歧，请相关角色用反例、边界、对象生命周期或失败场景挑战对方结论。分别保留已经反驳、仍未知、可并存和需要取舍的观点，不以投票替代决定。
4. **协调者综合**：核查角色输出的来源，识别共享问题与真实冲突，提出候选方案、后果、建议及不确定性。独立角色意见不能升级为用户访谈、市场事实或已接受需求。
5. **向负责人提问**：只提交确实需要其经验或权限的问题；可查事实由团队自行核实。收到答案后重演受影响场景，并让相关角色检查后果，必要时再追问。

没有委派能力时明确说明“未进行独立多 Agent 讨论”，由当前开发者分视角检查并标注局限。不能把一个回复里的多段角色口吻写成多人讨论结果。工具或资源不足时缩小讨论范围，不捏造执行记录。

## 一个有效问题应包含什么

| 内容 | 要求 |
|---|---|
| 已知与冲突 | 引用真实案例、材料或现行决定，说明哪些已经确定、哪些尚不确定。 |
| 必要决定 | 说明这次需要回答的具体规则或取舍，而不是“还有什么需求”。 |
| 影响 | 指出不同答案会改变哪些用户结果、范围、权限、质量或实施条件。 |
| 候选与建议 | 给可行选项及代价；有依据时给建议，没有足够依据时说明如何取得证据。 |
| 回答后的复核 | 明确需要用哪个反例或边界检查回答，涉及哪些资料应同步。 |

先问会推翻目标或影响大范围设计的问题，再问局部细节；每轮围绕可共同决定的少量问题，不能把长问卷一次倒给用户。开放问题适合调查实际经历，选项适合明确取舍；不要用封闭选项替用户限制真实问题。

## 从真实事件推导遗漏

沿“谁在什么条件下开始—操作与信息从哪里来—成功结果归谁—失败后谁处理—如何退出、纠错或终止”回放完整任务。进一步检查首次使用、权限变化、重复、取消、中断、部分成功、历史数据和跨角色交接；仅展开当前产品真正存在的情况。

发现缺口要给出依据、缺失后果、候选处理及建议。用户提出的方案与要解决的问题分别验证；表面功能完整时仍要问流程能否闭环、责任是否有人承担。

## 回答后的工作

区分事实补充、业务决定、偏好和新增建议，保留真实来源。把决定放回正常、异常和跨功能场景检查，说明新发现的冲突；不能只记录一句答案就宣布全部规则明确。

前期主动形成全局理解，后续复用仍有效的认知。只因版本、外部条件、范围或证据出现新差异才重新打开相应问题；不要每个阶段重新询问产品愿景。

关键语义能够判断、最低标准明确、阻断性取舍已有有权来源、剩余未知有具体影响和处理路径时，本轮讨论可以结束，并继续已授权的独立工作；讨论结束不等于开发结束。依赖未答问题的工作保持阻断。沉默、模型偏好和等待时长都不是答案。
