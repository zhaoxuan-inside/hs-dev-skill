# 后端框架设计

适用于服务端应用内部的框架与代码组织决策。明确模块边界、依赖方向、运行模型和外部适配方式，确保已确认的业务契约可以实现和验证。业务数据、接口与方法契约由 [backend 专业入口](../hs-dev-backend/SKILL.md)处理；Web 前端结构由 [frontend framework 专业入口](../hs-dev-framework-frontend/SKILL.md)处理。涉及多个服务或跨端协作时，只加载实际参与边界的专业入口。

## 设计方法

沿用当前过程的活动、目标对象及授权范围；本 Skill 提供专业检查，不另建任务或扩大阶段范围。只读评估仅报告发现，不实施修改。

1. 从已有代码、调用链、数据所有权和部署环境确认现状；区分实际约束与待验证假设。
2. 按业务职责和变化原因划分模块，说明每个模块拥有的数据、不变量及对外接口。层次应隐藏实现细节并约束依赖方向，不为模式本身增加层级。
3. 根据运行场景确定请求处理、后台任务、消息、事务和持久化边界；说明同步/异步选择、失败传播及进程重启后的状态恢复。
4. 把数据库、消息系统、文件系统和第三方服务置于明确的适配边界；业务规则依赖稳定契约，配置负责选择真实资源，测试替身不进入正式业务路径。
5. 仅针对明确的质量目标选择缓存、并发控制、隔离、重试、限流或可观测机制，并说明资源成本、失效模式和验证办法。
6. 只有现有技术或框架无法满足已知约束时才评估更换；使用相同的运行、维护、迁移及团队约束比较候选方案。

## 执行检查

- [ ] **核实输入与现状**：定位本次目标、业务契约、质量约束及相关代码。涉及具体框架时，从依赖清单、锁文件、启动入口和配置确认实际框架与版本；新项目尚未选型时明确候选及约束。事实、假设和待决定事项分别记录，必要业务决定缺失时返回当前过程，不自行补齐。
- [ ] **选择适用条目**：按下表只读取本次决策涉及的清单，并从中选取适用条目。已有有效设计直接复用；不因引用清单就新建阶段 README、固定六套环境或独立 Mock 服务。环境数量、文档形式和替身方式应符合当前项目的明确约束及实际验证需要；不适用条目说明理由，不能以此跳过已明确要求。
- [ ] **形成具体决定**：把所选设计方法落实到模块、接口、依赖或运行边界。涉及依赖注入、事务、任务调度等框架机制时，核对当前版本的官方契约或现有实现证据，记录适用条件；不能将其他版本或框架的行为当作事实。只比较会影响本次决定的候选。
- [ ] **选择验证方式**：依据下表核验关键决定。可执行检查按任务范围开展；纯设计任务可以交付静态证据及后续验证计划，但计划不能标记为已验证。关键未知若可能推翻设计，先做授权范围内的最小实验，或明确交接缺失条件。
- [ ] **交付与停止**：逐项关联约束、决定、代码或设计位置、验证结果及剩余风险。授权范围内的工作完成后停止，不自动安装框架、更换技术栈、迁移数据或扩展到下一活动。

### 验证选择

只选择本次受影响的机制，不要求每项任务执行全部检查。

| 涉及的决定 | 可用的核验方式与证据 |
|---|---|
| 模块职责、依赖方向和适配边界 | 对照实际导入、调用和数据访问关系；适用时运行已有依赖规则检查或针对性的边界测试，核对设计与代码是否一致 |
| 启动、依赖注入和运行配置 | 核对启动及注册链路；涉及落地修改时执行适用的构建、最小启动或配置校验，缺失配置和错误装配应有可解释结果 |
| 事务、并发、异步任务、超时和重试 | 选取受影响的成功及失败场景，检查提交/回滚、重复处理、资源释放和失败上限；以针对性测试或最小实验记录结果 |
| 外部资源和测试替换 | 核对契约与替换入口；按需要做契约或集成验证，明确模拟覆盖范围及尚未真实接入的部分 |
| 性能、容量或隔离机制 | 对照明确的目标和运行条件做最小测量或隔离验证，记录条件与结果，不以采用缓存、队列等机制本身证明目标达成 |

## 产出与边界

交付本次需要的模块及层次职责、依赖方向、关键运行/失败场景、框架取舍和验证依据。每个已选检查项记录 `对象／约束与决定／状态／证据／未决项`；状态为“通过、未通过、不适用、未验证”，不适用说明理由，未验证说明缺失条件和后续验证方式。简单任务可以直接回复，不强制新增设计文档。

业务规则或 API 语义未确定时返回当前过程，由 backend 专业入口协同澄清；不擅自补充产品行为。当前过程负责任务范围、执行和确认；本 Skill 不要求加载整套 C、D 或 E 阶段资料，不以专业自检代替人工验收。
