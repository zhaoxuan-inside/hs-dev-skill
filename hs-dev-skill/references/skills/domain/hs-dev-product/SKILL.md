# 产品分析与设计

负责愿景、定位、调性、功能完整性、行为、交互及整体关联。产品层须明确业务信息含义、角色权限、状态、操作结果和副作用；具体 API、存储结构及技术机制交由工程设计，不因“不设计技术契约”遗漏业务语义。

沿用当前过程已选定的活动、目标对象及上下文；专业职责不增加活动范围。不读取 workflow 总目录或整阶段资料。只有发现具体专业缺口时，向当前过程说明缺失的决定或证据，由该过程选择对应活动；已加载的共同约束不重复读取。

当前过程负责活动选择、任务推进和确认，本 Skill 提供所选活动内的专业分析方法。维护已有功能不从愿景重新开始；评审仅报告问题与证据，未授权不实施修改；只读任务不初始化、创建任务或刷新索引。

## 执行清单

- [ ] **核实基线**：定位当前活动、目标功能、授权范围、有效上游及需求来源。区分用户决定、现状事实、假设和建议；代码证明现有行为，不能自动证明期望行为。决定冲突时说明冲突及影响，不自行选取方便实现的版本。
- [ ] **选择专业检查**：只读取[产品工作方法](references/product-work.md)中命中当前活动的章节及当前过程已选活动清单。复用已确认且未受影响的决定；不把全部 A/B 活动、角色或通用能力变成必做项。
- [ ] **分析并形成结果**：按所选方法给出可判断的规则和场景，关联需求来源及功能标识。必要决定缺失时交由当前过程澄清，暂停依赖该决定的设计，其余独立工作可以继续；不擅自补功能、降级行为或优先级。
- [ ] **核验结果**：逐项核对适用活动标准，沿角色、前置条件、输入、状态、结果及副作用演练受影响路径；检查需求覆盖及跨功能冲突。发现范围外遗漏说明依据和影响，不静默扩范围或缩减分母。
- [ ] **交付与停止**：按下述格式交付结果、证据和未决项；完成当前范围后停止，不自动进入技术设计、实施或发布。人工确认由统一模块按任务模式处理，不代签或把暂缓当通过。

## 证据与交付

每个已选检查项给出 `对象／需求或决定依据／状态／证据／未决项`，状态使用“通过、未通过、不适用、未验证”；说明不适用理由、失败影响及未验证条件。结果可以直接回复或更新现有产物，不强制新增文档、功能编号体系或调研报告。

区分文档一致性审阅、场景演练、原型操作、真实用户研究和真实系统验证；每类证据只支持其实际覆盖的结论。记录对象版本、场景、预期和实际结果；纯计划不能标记验证通过，未经用户研究不能宣称需求已被用户验证，专业自检不能代替人工验收。

涉及竞品、市场或其他外部事实时，按实际问题查证并记录来源和时间；没有调研时明确未知，不从常识编造结论。已有有效来源可复用，普通功能维护不自动升级为市场调研。
