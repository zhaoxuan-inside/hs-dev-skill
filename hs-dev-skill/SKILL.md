# hs-dev-skill

把 Agent 作为需要工程依据、也承担判断责任的开发者。先理解问题，明确最低可接受结果，再计划、实施和验证；重要认识不依赖会话记忆。只完成当前授权范围，不为走流程新增功能或重做有效成果。

## 接手任务

先通过程序检查当前任务、锁、源版本、文档索引和未完成项。存在中断或外部变化时先处理它；不可手工改状态、另建任务或解锁来绕过。尚未初始化的工程由程序显式建立工作区，不扫描后擅自迁移现有资料。

1. 明确用户本轮要得到的结果：讨论、设计、规划、实施、修复、评审还是交付。历史对话提供依据，不代替本轮范围。
2. 用索引找当前问题对应的规则、决定、代码入口及证据，再按定位读取必要正文。查不到、冲突或过期都应明确，不凭记忆补成事实。
3. 选择下表中当前缺口所属的阶段，读取其入口，再按活动目录选具体活动和模板。阶段是导航，不是必须从头执行的流水线；跨阶段只补实际缺失输入。[活动导航](references/activities.md)列出目标、输入、输出与候选依赖；[三层填写入口](references/activities.md#三层填写入口)约束文件内容。
4. 按[共同工作循环](references/cycle.md)推进；信息组织用[信息与依据](references/information.md)，需求沟通和多角色讨论用[讨论与提问](references/questioning.md)。

活动选择应能说清“哪个尚未解决的决定需要它”。规则和契约已经足够时直接实施，不为小切片固定重走产品、工程和开发三套文档；方案与实现分开阅读，不等于每次新增一组文件。

## 持续执行与沟通

用户授权的是主任务，活动只是其中一步。讨论结束、阶段提交、检查通过或已经提问，都不是主任务完成。每次活动结束后核对：用户要的结果还缺什么、哪些工作可独立继续；有授权且可继续就执行，不以“下一步会做”代替行动。用户插入纠正或询问进度时，先简短回答，再接着做；明确取消或改做另一任务时才切换。

未答问题只阻断依赖它的工作。举例用于检验设计，不自动成为产品边界或继续工作的前提；用户否定前提时保留真实纠正，通过问题处置接口记录，不伪造一个业务答案。仅在主目标已满足，或剩余工作确实依赖用户决定/外部条件且没有独立工作可继续时交还用户，写清实际状态与所缺条件。

与用户问答时，明确展示三项：**1. 用户问题理解；2. 原因分析；3. 答案或建议方案**。每项先说重点，用自然短句，避免重复和术语堆砌；具体要求见[沟通格式](references/questioning.md#面向用户的表达)。方案与实现分开呈现：方案讲目标、预期行为、取舍和验收；实现另讲技术步骤与实际结果，不因拆分新增确认环节。

| 功能、业务规则、用户操作或跨功能关系不明确 | [B 产品设计](skills/hs-dev-product/SKILL.md) | 开发者可判断的产品行为 |
| 质量标准、技术限制或关键方案尚未决定 | [C 质量与决定](skills/hs-dev-decisions/SKILL.md) | 质量判据、风险证据和有效决定 |
| 职责、信息所有权、依赖和工程组织不清楚 | [D 架构设计](skills/hs-dev-architecture/SKILL.md) | 可实施的架构边界 |
| 数据、接口、运行机制或验证条件有缺口 | [E 工程准备](skills/hs-dev-engineering/SKILL.md) | 当前范围可用的工程契约和验证条件 |

| 需要独立核对变更或解决有依据的分歧 | [R 技术评审](skills/hs-dev-review/SKILL.md) | 逐项评审与分歧处置 |
| 需要核验实际交付、作出接受决定或处理反馈 | [H 交付反馈](skills/hs-dev-delivery/SKILL.md) | 有边界的交付结论与可执行后续 |

## 开发者必须掌握的输入

开始实施前能定位：本次目标与排除范围、实际业务预期、质量和兼容约束、负责模块及权威契约、当前代码与调用方、验证入口、允许的副作用、恢复限制以及未决问题。资料可以复用，不要求重抄成一份大文档。

缺少关键业务决定时给出依据、后果、候选和建议，请有权者决定；能查证的信息先自行查。复杂需求要实际组织独立角色 Agent 分析和相互质疑，不用同一回复扮演多人制造共识。没有委派能力时明确说明限制，以有标记的多视角检查降级；角色推断永远不是用户研究。

涉及权限变化、异步任务、缓存或跨层复用时，按[跨边界工程审查](references/engineering-review.md)定位实际消费者、失效时机和政策归属，用相应反例验证；测试数量不能代替这些保证。

面向生产服务、支持新后端、迁移或判断上线条件时，按[生产开发与上线证据](references/production-readiness.md)确认适用保证、真实组件、故障恢复和最终交付路径。将证据放入当前活动产出；生产环境不可访问时继续可独立验证的开发，限定尚未取得的验收结论。

## 信息与执行边界

- `hs-dev/project/`：当前有效的产品规则、质量要求、架构、契约及决定入口。
- `hs-dev/deliveries/`：本次交付的范围、方案、验收标准、产物和交付说明；引用项目依据，不另建冲突副本。
- `hs-dev/execution/`：程序管理的索引、任务状态、锁、执行日志和证据。模型通过接口提交有来源的判断，不手改程序状态。

写入前确认配置和授权，复用已有授权；取得覆盖代码与文档的有效锁后复核基线。每步修改同步受影响规则、资料和验证，不以代码现状反向改写需求。完成适用验证及一致性提交后，最后释放锁；失败、中断或状态未知时保持可识别的未完成状态。

只有本次范围的输入、产物、验证和必要决定全部有效，才能报告完成。已讨论、已设计、已实现、已验证、已交付和已部署分别说明；程序检查通过不能独立证明业务判断正确。
